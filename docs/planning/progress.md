# Wonboard 로컬 구현 진행 기록

2026-09-05. M0/M1 초기 편집기 이후 지원이 요청한 글 목록·첨부 탭·영상 링크를 추가했다. 전체 계획의 완료나 서버 준비 완료를 의미하지 않는다. 오늘 작업을 `codex/web-editor-checkpoint` 브랜치의 열린 PR로 보존하는 체크포인트이며 merge·배포는 범위 밖이다.

공개 이미지 저장소는 [후속 결정 기록](./storage-decision.md)에 남기고 결정을 보류했다. Google/ImgBB/자체 중계 중 어느 것도 최종 채택하지 않았으며, 이후 작업자가 이전 Drive 구현 계획을 자동으로 이어서 실행하지 않는다.

## 2026-09-07 공개 접근과 실제 외부 이미지 표시 검증

지원이 직접 사진을 첨부하고 내보내기에서 공개로 등록했지만, Site 전체가 `Only you`여서 이미지 주소도 익명 요청에 401을 반환했다. 원보드의 게시 등록과 Sites의 사이트 접근 정책이 다른 설정이라는 것이 실제 원인이었다. 이후 지원이 초안·원본 보호를 확인한 뒤 시험 Site를 인터넷에서 접근 가능하게 바꾸고, 이미 공개로 지정한 사진 한 장을 검증하도록 명시적으로 승인했다.

- 기존 Work 작업 `6a9e143d-6b18-83ee-a349-a7ad9443b813`이 실제 배포 코드와 소유자 검사를 확인한 뒤 같은 Site의 접근을 `Anyone on the internet / public`으로 변경했다. 접근 정책 revision은 2다. 소스 버전 2·환경 revision 1·기존 `succeeded` 배포는 유지했고 재배포는 필요하지 않았다.
- Work 작업은 문서 1건·원본 1건·게시 레코드 1건이며 공개 대상도 승인된 1개뿐임을 읽기 조회로 확인했다. 실제 배포 checkout의 82개 단위 테스트와 빌드가 통과했고, 정적 파일 11개에서 문서 내용·식별자와 소유자 값의 노출을 검사했다고 보고했다. 추가 파일 공개·사용자 자료 변경·DB 마이그레이션·GitHub 작업은 하지 않았다.
- 별도로 이 로컬 작업의 `pnpm typecheck`와 81개 단위 테스트를 재실행해 통과했다. 이 수치는 Work checkout의 82개와 구분한다.
- 로그인·쿠키·Authorization 없이 실제 게시용 이미지 URL을 GET/HEAD한 결과 모두 200, `image/png`, 225,182바이트였다. SHA-256은 `5a0c8fc26bae950de6a1f020a5b658f38b28ebc104f80b6c69b3848e52eb1b45`로 Work가 보고한 게시용 객체와 일치했다. `Cache-Control: no-store`, `Cross-Origin-Resource-Policy: cross-origin`, 만료 query 없는 기존 주소를 확인했다.
- 같은 공개 상태에서 실제 문서 본문·문서 목록·원본 사진·게시 상태 목록 API에 익명 GET을 보내 모두 `401 application/json`을 확인했다. 임의의 클라이언트 사용자 식별 헤더를 보낸 목록 요청도 401이었다. 이는 실제 다른 계정으로 로그인한 시험을 대신하지 않는다.
- 사용자 Chrome 프로필과 분리된 새 Chrome 문맥에서 다른 출처의 실제 HTML 페이지를 열었다. 외부 img 요청에 쿠키·Authorization이 없고, 이미지의 자연 크기는 **1200×512**, 로드 완료 상태였다. 프레임워크 오류 화면이나 브라우저 오류·경고는 없었고 실제 표시 화면을 캡처해 확인했다.
- 같은 익명 브라우저로 Site 루트를 열면 원보드 로그인 안내가 보이고 문서 편집기는 없었다. 지원의 기존 로그인 크롬에서는 새로고침 후에도 본문·사진·문서 목록·저장 완료 표시가 유지됐다.

시험 주소는 [Wonboard Media Lifecycle Test](https://wonboard-media-test.b79fff42-6d7b-4203-81c5-342635917d97.chatgpt.site), 공개 사진 주소는 [게시용 PNG](https://wonboard-media-test.b79fff42-6d7b-4203-81c5-342635917d97.chatgpt.site/media/7d0e31bd-f7cc-4d3f-97ab-6d42638d2a59)다. API·브라우저 검증 결과와 두 스크린샷은 `/private/tmp/wonboard-public-check.7lBGy2/`에만 두었으며 시험 서버와 임시 브라우저는 종료했다. Browser 플러그인 스킬은 없어 외부 익명 시험에 기존 Playwright를 사용했고, 실제 사용자 크롬은 CUA로 확인했다. 새 도구나 의존성을 설치하지 않았다.

이번 완료 범위는 승인된 사진 한 장의 공개 접근과 외부 표시, 익명 문서·원본 접근 차단이다. 실제 다른 계정 로그인, 사진 업로드 후 재배포 지속성, 공개 철회·재공개, 실제 커뮤니티의 HTML 서식 호환, 장기 보존은 아직 검증하지 않았다. 사용자의 게시용 사진은 철회하거나 삭제하지 않았다. 원본은 UI에서 183KB였지만 다시 인코딩한 게시용 PNG는 약 220KiB이므로, 게시용 변환이 항상 용량을 줄인다고 표현하지 않는다. 원본 비공개 안내는 여전히 맞으며, 게시 등록과 실제 외부 접근 가능 여부를 나눠 보여주는 UI 개선은 별도 후속 과제다.

## 2026-09-07 실제 Site의 첫 설치 화면 복구

지원이 크롬 첫 접속에서 멈춘 화면의 수정과 소유자 연결 완료를 승인했다. 실제 화면은 로그인 실패가 아니라 서버의 `WONBOARD_OWNER_ID`가 없는 상태였고, 안내문만 있어 사용자가 계속할 수 없었다. 기존 시험 Site에만 변경을 적용했으며 이번 후속 작업에서는 `Only you`를 유지했다.

- `SitesGate`에 한국어/영어 설치 안내, 상태 재확인 버튼, 로그인한 본인의 Site별 연결 ID를 읽는 접힌 안내를 추가했다. ID 조회는 기존 읽기 전용 API를 사용하며 방문자에게 소유권을 주지 않는다. 서버의 소유자 일치 검사는 바꾸지 않았다.
- 실제 크롬의 새 UI에서 Site별 ID를 확인하고 기존 Work 작업에 전달했다. Work 작업은 공식 도구로 `WONBOARD_OWNER_ID`를 secret 환경변수에 저장하고 소스 버전 2·환경 revision 1의 비공개 배포가 `succeeded`라고 보고했다. 소유자 값은 저장소에 기록하지 않는다.
- 크롬에서 첫 실행 안내로 자동 전환된 것을 확인했다. 설치 승인 범위에서 자료 저장·공개 시점 안내를 확인한 뒤 편집기와 글 목록까지 진입했다.
- `[시험] Sites 저장 확인` 문서 한 개를 작성했다. 실제 Site에 저장됐다는 표시를 확인하고 새로고침한 뒤 제목, 한글/영문 본문, 세 문단, 글 목록이 복원됐다. 첫 설치 안내는 다시 나타나지 않았으며 수집한 콘솔 오류·경고는 없었다.
- 합성 70바이트 PNG 첨부는 브라우저 자동화의 `fileChooser.setFiles`가 `Not allowed`를 반환해 수행하지 못했다. 제한을 우회하지 않았다. 현재 시험 문서의 사진은 0장이며 실제 R2 업로드·복원을 통과했다고 기록하지 않는다. 개인 사진이나 기존 초안은 업로드하지 않았다.
- 로컬 `pnpm typecheck`, `pnpm test` 81개, `pnpm build:sites`가 통과했다. Sites E2E는 새 설치 상태 확인 시험을 포함해 최종 3개 통과(7.5초). 계정 확인 중 쓰기 요청이 없고 390px 화면 안에 연결 ID가 들어오는 것도 검사했다. E2E 저장소·인증은 여전히 로컬 대역이다. 빌드의 500kB 경고는 남아 있다.

현재 시험 주소는 [Wonboard Media Lifecycle Test](https://wonboard-media-test.b79fff42-6d7b-4203-81c5-342635917d97.chatgpt.site)다. 다음은 실제 사진 한 장의 비공개 저장·복원 검증이다. 익명 이미지 공개, 외부 삽입, 재배포 후 이미지 보존과 철회 검증은 아직 남아 있다. 아래 기록은 각 이전 단계의 검증 시점을 보존한다.

Work 작업의 최종 결과는 소스 버전 2·환경 revision 1의 `succeeded`, `Only you`, 소유자 1명·기타 사용자/그룹 0명을 확인했다. 공식 Sites 연결·Drizzle 변경 19개 파일의 재사용 patch를 해당 작업의 아티팩트로 제공했으며 보고된 ZIP SHA-256은 `592d0ae9394f89a66bb442fad1292732be261a4b5fa7689f563f819b8e2c961d`다. 실제 환경값·계정 식별자·설치 UI 세 파일 변경을 제외했다고 보고했다. 이 아티팩트는 아직 로컬에 내려받아 검사하거나 모노레포에 적용하지 않았다. 다음 코드 동기화 때 원본 ZIP과 현재 dirty 파일을 모두 보존하고 patch 내용을 먼저 검토한다.

## 2026-09-07 Sites Work 경로의 실제 생성 시험

지원의 후속 승인으로 별도 ChatGPT Work 작업 `6a9e143d-6b18-83ee-a349-a7ad9443b813`을 생성했다. 일반 Chat 대화와 달리 이 작업에서 실제 Sites 생성 도구가 확인됐다는 응답을 받았고, ChatGPT의 Sites 목록에서도 새 `Wonboard Media Lifecycle Test`가 `Only you · 게시되지 않음` 상태로 생성된 것을 직접 확인했다. 기존 `Onsoon Labs` 항목은 `8월 12일 · Only you` 상태로 유지됐으며 수정하지 않았다. 생성 확인과 배포·실제 인증·이미지 보존 성공은 별개다.

- 미커밋 Sites 구현과 계획서를 포함한 78개 파일을 `wonboard-sites-source.zip`으로 이 Work 작업에 첨부해 전달했다. 압축 크기 177,522바이트, SHA-256 `488b9af70a293c01fb12ccfcb80e5178da982c438be27c46212b8475d8178c68`이다.
- 모든 `.env` 파일, `.git`, `.DS_Store`, 개인 초안·사진, 의존성 설치 폴더, 빌드 결과와 로그를 제외했다. 실제 로컬 비밀번호 값의 후보 파일 미포함을 값 출력 없이 검사했다.
- 새 시험 Site에 필요한 공식 Sites 연결·Drizzle 도구와 초기 시험 DB 생성은 승인됐다. 기존 데이터·사이트, 새 유료 구매, 실제 사용자 자료 공개, GitHub push·PR·merge는 범위 밖이다.
- 전달 시점의 로컬 소스로 `pnpm typecheck`, `pnpm test`(81개), `pnpm build:sites`를 다시 실행해 통과했다. 500kB 번들 경고는 그대로다. 이 재실행에서는 브라우저 시험을 추가하지 않았으며 아래 E2E 수치는 이전 실행 기록이다.

후속 결과로 Work 작업이 최초 비공개 배포 `succeeded`를 보고했다. 주소는 [Wonboard Media Lifecycle Test](https://wonboard-media-test.b79fff42-6d7b-4203-81c5-342635917d97.chatgpt.site)다. Work 결과에는 허용 사용자 1명·다른 사용자/그룹 0명, D1 네 테이블이 비어 있음, R2 `MEDIA` 연결 준비가 기록됐다. 해당 checkout에서는 빌드와 82개 단위 테스트가 통과했다고 보고했다. 이 수치는 로컬에서 직접 실행한 81개와 구분한다.

실제 `/api/sites/identity` 주소를 브라우저에서 열어 플랫폼 로그인 → 기존 ChatGPT 계정 선택 → 시험 Site로 기본 프로필을 공유하는 첫 동의 화면까지 확인했다. 동의는 누르지 않았다. 표시된 범위는 이름·사용자명·이메일·프로필 사진이며 ChatGPT 대화 기록은 포함되지 않는다. 승인이 끝난 뒤 Site별 ID를 해당 Work 작업에 전달하고 서버의 소유자 설정에 연결하는 것이 재진입 지점이다.

별도로 쿠키 없는 HTTP 요청에서 `/api/sites/identity`와 `/api/documents` 모두 401과 플랫폼 로그인 HTML을 반환했고 문서 JSON은 반환하지 않았다. 이는 현재 비공개 Site의 접근 차단 확인이며, 공개 전환 후 애플리케이션의 익명 접근 제어 시험은 아니다.

소유자 설정과 합성 이미지의 저장·익명 공개·외부 삽입·로그아웃·재배포·철회 검증은 아직 완료하지 않았다. Work checkout의 공식 Sites 연결과 초기 마이그레이션 변경은 아직 로컬 모노레포로 회수하지 않았다. 신규 Site 중복 생성이나 로컬 대역 결과의 실배포 승격을 하지 않는다.

## 2026-09-07 개인 Sites 설치판 로컬 구현

지원은 별도 도메인 없이 사용자 각자의 ChatGPT Sites에 기존 작성기를 설치하는 방향과, 별도 시험용 Site에서 합성 이미지 한 장을 공개하는 검증을 승인했다. 기존 글 목록·편집기·사진 UI를 유지하고 짧은 설치 안내를 추가한다. 상세 실행 범위와 재진입 지점은 [개인 Sites 계획](./personal-sites-plan.md)을 따른다.

후속 요청으로 로컬 구현까지 진행했다. Sites 로그인 진입·첫 안내, 소유자 전용 문서/원본 저장 API, 사진 변환·공개 URL·HTML 복사·공개 철회 기능을 기존 UI에 연결했다. 로컬 모드의 로그인·IndexedDB·ZIP 백업은 유지했다. 새 외부 의존성이나 lockfile 변경은 없다.

현재 작업의 도구 목록에는 Sites 생성·저장소 연결·버전 저장·배포 호출이 없다. 지원이 지정한 ChatGPT 대화 「계획서 구현 가능성 검토」로 별도 시험 요청을 보냈고, 최종적으로 그 대화에서도 실제 생성·배포 도구가 없어 실행하지 못했으며 시험용 URL이 없다는 답을 받았다. **실제 ChatGPT 인증·D1·R2·공개 배포는 완료로 판정하지 않는다.** 기존 Onsoon Labs Site·도메인·사용자 초안·실제 사진을 변경하거나 외부로 보내지 않았다. GitHub push·PR·merge도 하지 않았다.

### 이번에 동작시킨 흐름

- 기존 글 목록·편집기·첨부 UI를 유지하면서 저장 위치를 “내 ChatGPT Site”로 표시한다. 선택한 글의 원본만 내려받고 목록에는 가벼운 요약을 사용한다. 기존 localhost 글은 자동 이동하지 않는다.
- 첫 안내는 ko/en이며 초안/원본의 비공개, 공개한 사진의 외부 노출, 백업·권리·플랫폼 조건을 설명한다. 확인란은 자동 동의하지 않는다. [Sites 약관](https://openai.com/policies/chatgpt-sites-terms/) 링크가 실제로 열리는지 확인했다.
- 로그인과 소유자 권한은 별개로 검사한다. 플랫폼의 Site별 ID가 설치자가 정한 서버 값 및 설치 DB의 ID와 일치해야 편집한다. 공개 첫 방문자의 소유권 선점은 허용하지 않는다.
- 자동 저장은 이미지 업로드 뒤 문서를 저장하며 충돌·실패 시 저장 완료라고 표시하지 않는다. Sites 모드의 오프라인 영속 복구는 아직 없으므로 저장 실패 중 탭을 강제 종료하면 복구를 보장하지 않는다.
- 명시적 내보내기에서 표시 폭에 맞춘 PNG/JPEG를 준비하고 공개한다. 제목 변경과 다시 공개해도 주소는 유지한다. 초안에서 사진을 빼는 것과 공개 철회는 분리한다.
- 내보내기 대화상자는 서식 복사, HTML 복사, 공개 주소 목록, 전체 공개 철회를 제공한다. 모바일에서도 내보내기 버튼을 열 수 있게 수정했고 390px 경계를 측정했다.

### 이번 실행에서 검증한 범위

- `pnpm typecheck`, `pnpm test`: 6개 파일 81개 단위 테스트 통과. 실제 SQLite SQL로 소유자 확인·입력 검사·버전 충돌·공개/철회/주소 보존을 검사한다. R2와 플랫폼 인증은 시험 대역이다.
- `WONBOARD_TEST_CHANNEL=chrome pnpm test:sites --project=chromium`: 신규 2개 흐름 최종 재실행 통과(7.0초). 안내 → 글·사진 저장 → 새로고침 복원 → 공개 확인 → HTML → 익명 브라우저의 다른 origin에서 실제 이미지 표시 → 제목 변경 후 같은 주소 → 철회 404 → 다시 공개 200 → 한국어 모바일 내보내기를 확인했다. 외부 페이지의 한글도 확인했다.
- 신규 화면의 URL/제목·실제 컨트롤·오류 오버레이 부재·브라우저 콘솔을 검사했다. 페이지 예외와 콘솔 오류/경고는 0개였다. 1280×720 영어, 390×844 한국어 화면을 캡처해 직접 확인했다. 스크린샷은 `/private/tmp/wonboard-sites-export.png`, `/private/tmp/wonboard-sites-mobile.png`에만 두었다.
- `WONBOARD_TEST_CHANNEL=chrome pnpm test:e2e --project=chromium`: 기존 로컬 회귀 20개 통과(23.0초). 합성 50장/20,000자 복원은 1,058ms였으며 실제 대용량 파일이나 외부 저장소 부하 측정과는 다르다. 의도한 저장 용량 실패 시험의 경고는 예상된 결과다.
- `pnpm build`, `pnpm build:sites` 통과. Sites 클라이언트 737.11kB(gzip 233.66kB), 내보내기 모듈은 실행 시 별도 로드하며 187.71kB(gzip 57.42kB), Worker는 23.60kB(gzip 6.94kB)다. 500kB 번들 경고는 남아 있다. Worker 산출물에 Node 전용 런타임 참조가 없는지 검사했다.
- Browser 플러그인 스킬이 없어 기존 Playwright 경로를 사용했다. 기본 Playwright Chromium 바이너리는 없었고, 설치돼 있는 Chrome을 사용했다. 샌드박스의 Chrome 실행 거절은 승인된 격리 실행으로 해결했다. 사용자 Chrome 프로필은 사용하지 않았으며 브라우저나 의존성을 설치하지 않았다. 이번 실행에서 Firefox/WebKit은 재검증하지 않았다.
- 최초 시험 PNG의 잘못된 바이트는 CRC와 압축 데이터를 직접 생성하는 유효한 합성 PNG로 교체했다. 브라우저가 가짜 응답 페이지에서 loopback 접근을 차단한 오류는 별도 실제 로컬 HTTP 서버로 시험했다. 보안 설정을 꺼서 통과시키지 않았다. 실제 HTTPS Sites/커뮤니티 시험은 여전히 별도로 필요하다.

`build:sites`는 플랫폼에 연결하기 전 Worker 빌드 확인 단계다. 공식 Sites 플러그인·Drizzle 스키마/마이그레이션, 실제 소유자 연결, `.openai/hosting.json`, 실제 저장소 준비 및 배포는 남아 있다. 상세 파일과 이어갈 절차는 [개인 Sites 계획의 인계 계약](./personal-sites-plan.md#구현된-코드와-배포-인계-계약)을 따른다. 이전의 테스트 기록은 아래에 그대로 보존한다.

## 검증

### 2026-09-06 PR #2 리뷰 수정

- ZIP 내보내기가 압축 전 합계뿐 아니라 헤더를 포함한 최종 파일 크기도 검사한다. 가져오기 상한을 넘는 백업을 성공으로 내려주지 않는다.
- 제목 입력과 문서 검증이 같은 10,000 UTF-16 코드 단위 상한을 사용한다. 긴 제목 붙여넣기로 자동 저장과 백업이 함께 막히지 않는다.
- IndexedDB 열기가 다른 탭에 막히면 안내하면서 요청을 계속 기다린다. 차단이 해제된 뒤 같은 요청의 성공으로 저장소 연결을 완료한다.
- 저장·백업 사본에는 본문에서 사용하는 사진만 남긴다. 현재 편집 세션의 원본은 실행 취소를 위해 보존하며, 다시 열 때 정리한다. 실행 취소 보관분 때문에 100장 제한에 걸리면 저장 후 다시 열도록 안내한다. 외부 저장소 파일을 삭제하는 기능은 아니다.
- 읽기 전용 문서에서도 다른 문서 선택·새 문서·백업 복원으로 이동할 수 있다. 충돌 사본은 현재 탭에 보존해 다시 선택하고 백업할 수 있으며, 탭 종료 전 경고한다. 충돌 사본의 새로고침 후 보존을 보장하지 않으므로 종료 전에 백업해야 한다. 알 수 없는 형식의 저장 원본은 변경하지 않는다.

검증: `npm run typecheck`, `npm test`(4개 파일 71개), `npm run build` 통과. Chromium/Firefox/WebKit의 전체 E2E 60개가 통과했다(1.0분). ZIP 경계와 차단된 저장소 열기는 수정 전 실패를 재현했다. 사진 100장 시험은 작은 합성 PNG의 삭제·실행 취소·다시 실행·재열기 후 추가를 검사하며, 실사진 100장의 안전 용량을 뜻하지 않는다. 초기 E2E의 전체 선택/이름 선택자 문제와 WebKit 화면 배율에 따른 테스트 이미지 크기 차이는 시험 코드를 수정한 뒤 전체 재실행했다.

테스트는 격리된 브라우저 문맥과 임시 개발 서버에서 실행했고 사용자 프로필·초안·쿠키를 공유하지 않았다. 공개 후보와 빌드에 로컬 계정 값이 없음을 값 출력 없이 확인했다. 공유 JS 674.96 kB(gzip 212.91 kB)의 기존 500 kB 초과 경고는 남는다. 실제 OS 한글 입력기와 공개 이미지 저장소 결정은 이번 수정 범위에 포함하지 않았다.

- 사진 호스팅의 비용·권한·운영 책임은 [후속 이슈 #1](https://github.com/jiwonschol/wonboard/issues/1)에 남겼다. PR과 연결하되 자동 종료하지 않는다. 실제 외부 게시판 게시, 장기 보존, 대형 원본 부하는 이번 체크포인트에서 재시험하지 않았다.

### 앞선 구현 단계의 검증 기록

- 단위 테스트 68개 통과: 기존 62개에 계정 검증·세션 발급/만료/로그아웃·설정 누락·교차 출처 차단·입력 크기와 재시도 제한을 추가했다.
- 브라우저 17개 흐름 × Chromium/Firefox/WebKit = 51개 통과. 기존 14개에 잘못된 비밀번호/로그인/즉시 로그아웃/초안 복원, 한국어 모바일/인증 서버 장애, 서버 세션 취소 후 초점 복귀와 초안 보존을 추가했다. 미디어 제공자는 결정론적 E2E에서 대역 응답을 사용한다. 이 검사만으로 외부 영상의 실제 재생까지 검증했다고 하지 않는다.
- 별도 격리 브라우저의 실제 제공자 확인: YouTube 공개 예제에서 currentTime=83, paused=false를 확인했다. Vimeo 공개 예제는 currentTime=42, paused=true, readyState=1까지 확인했으며 실제 재생 완료 판정은 보류한다. 사용자 초안이나 이미지는 외부로 보내지 않았다.
- 타입 검사와 프로덕션 빌드 통과. 편집기 공유 JS는 약 673kB(압축 약 212kB)로 빌드 크기 경고가 남는다. 대용량 원본 50장 부하 시험과 동일하지 않다.
- 실제 Codex 브라우저에서 한영 문장 작성, 언어 전환, 파일 선택으로 사진 삽입, 폭·설명·대체 텍스트 편집. WordPress 원본과 빈 문서 화면을 같은 너비로 대조했다.

WebKit의 Blob 저장에서 `Error preparing Blob/File data to be stored in object store`를 재현했다. 원본 바이트를 ArrayBuffer로 저장하고 읽을 때 Blob으로 복원하여 세 브라우저 사진 저장·복원 검증을 통과했다. 기존 Blob 형식도 읽는다.

## 완료 판정을 남겨 둔 항목

1. 실제 macOS 한글 입력기로 조합·확정·삭제·커서 이동을 확인해야 한다. 합성 이벤트나 문자열 주입은 이를 대체하지 않는다.
2. WordPress의 상단 배치·작은 간격·아이콘과 전체 설정 동작은 아직 완전 일치하지 않는다. [시각 대조 기록](../reference/wordpress-editor.md)을 따른다.
3. Office/HWP 문서의 서식·이미지 붙여넣기, 임의 원격 HTML 이미지 가져오기는 미구현이다. 합성 파일 이벤트 테스트는 OS 클립보드 전체 호환성 증명이 아니다.
4. 로컬 모드에서는 모든 초안의 원본을 함께 읽는 방식이 남아 있다. Sites 모드는 목록 요약과 선택한 문서 읽기로 분리했다. 실사진 부하·총량 제한·고아 파일 정리·저장 실패 복구·실제 배포 인증은 보강해야 한다. 외부 사용자를 받는 서비스로 배포하지 않는다.
5. Sites용 원본 저장·게시용 이미지 변환·공개 HTML 내보내기는 로컬 구현·시험까지 진행했다. 실제 Sites 연결·다른 계정 인증·재배포 지속성·공개 인터넷 검증은 남아 있다. 다른 소셜 로그인·게시판 서버·목적지 프로필·실제 외부 게시판 테스트·MCP·게시판 프리셋도 후속 단계다.

## 단일 사용자 테스트 로그인

지원이 지정한 계정은 Git에서 제외한 `.env.local`의 서버 전용 설정으로 보관한다. 비밀번호 값은 문서와 클라이언트 소스에 넣지 않는다. `apps/server/src/local-auth.ts`에서 확인하고 `vite-auth.ts`를 통해 개발/미리보기 서버에 연결한다. 새 의존성은 추가하지 않았다. 구현 시 [Vite 서버 플러그인](https://vite.dev/guide/api-plugin.html)과 [Node.js crypto](https://nodejs.org/api/crypto.html)를 확인했다.

세션은 HttpOnly/SameSite=Strict 쿠키로 8시간 유지하며 서버 재시작 시 만료된다. 설정 누락이나 초기 인증 서버 장애 때 편집기를 열지 않는다. 이미 열린 글은 세션이 만료되어도 메모리에서 버리지 않고 로그인 화면 뒤에 보존한다. 로그아웃 전에 저장을 시도하며 실패 시 백업을 안내한다. 다른 탭의 로그아웃은 창 초점 복귀 또는 최대 1분 간격 확인으로 반영한다.

이 기능은 로컬 편집기의 정상 진입을 제한한다. IndexedDB와 열린 문서의 암호화, 브라우저 개발 도구를 사용하는 로컬 접근자의 차단은 제공하지 않는다. 개발 서버는 loopback에만 바인딩하며 HTTP 요청의 Origin/Host를 확인한다. NAS나 인터넷에 그대로 노출하는 인증 설계가 아니다. 비밀번호가 빌드에 포함되지 않는 것과 `.env.local`의 일반/원본/절대경로 요청이 모두 HTTP 403인 것을 확인했다. 실제 Codex 브라우저에서 로그인 후 기존 `ai시대` 문서와 사진 1개가 보존된 것을 확인했다.

## 실행과 재진입

`pnpm install`, `pnpm dev`로 시작한다. 브라우저 저장은 출처별이므로 127.0.0.1과 localhost, 포트를 바꾸면 다른 초안 목록이 보인다. 중요한 글은 ZIP으로 백업한다.

이 환경에서는 설치 저장소를 `/private/tmp/wonboard-pnpm-store`, Playwright 바이너리를 `/private/tmp/wonboard-browsers`로 격리했다. 기존 설치 후 `npm run typecheck`, `npm test`, `npm run build`, `PLAYWRIGHT_BROWSERS_PATH=/private/tmp/wonboard-browsers npm run test:e2e`로 검증했다. 프로젝트 의존성 설치 정본은 pnpm lockfile이다.

지원은 실행 중 실시간으로 보고 있지 않을 수 있다. 다음 구현 전에 이 기록, 계획의 확정 결정, 실제 git 상태를 확인한다. 기존 초안·사용자 수정은 보존하고, 자동화 시험은 격리된 브라우저 문맥에서 한다. 서버 단계의 승인 범위·저장소 선택·공개 행위를 확인한 뒤 진행한다. 현재 로컬 구현 권한을 main push·merge·배포 권한으로 확대하지 않는다.
