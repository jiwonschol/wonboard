# 공개 게시글 한영 실전 대조 (2026-09-26)

## 지원 제공 커뮤니티 순위표의 사용 범위

지원이 제공한 [와플보드 2026년 9월 커뮤니티 순위](https://waffleboard.io/ranking)를 추가 출처 선정에 사용한다. 이미 다룬 디시인사이드·더쿠·루리웹·인벤·개드립 등과 겹치지 않는 상위권의 아카라이브, 엠엘비파크, 토스증권 커뮤니티, 인스티즈, 이토랜드 등을 우선 확인한다. 접속·robots 제한이 있으면 해당 호스트를 건너뛰고 허용된 다른 순위 사이트로 옮긴다. 이 표에는 이용자 연령 자료가 없으며, 게시글 문체로 연령을 추정하지 않는다. 순위 페이지는 수치를 MAU로 표시하지만 [와플보드의 별도 설명](https://waffleboard.io/blog/dcinside-arcalive-etoland-complete-comparison)은 이와 비슷한 자사 수치를 방문 횟수로 다루고 고유 이용자와 구별한다. 따라서 이 문서에서는 순위와 수치를 도달 범위의 정확한 추정치로 쓰지 않고, 사이트를 고르는 참고 자료로만 쓴다.

## 새 출처와 독립 첫 평가

이전 차수의 실패를 보고 코드를 고친 뒤, 별도 수집자가 새 공개 글의 정답 구간과 채점 규칙을 검사 전에 고정했다. 아래 수치는 **첫 예측**이며 뒤이은 같은 표본 재실행을 합격 점수로 세지 않는다. 한국어는 출처 URL에서 HTTP 200으로 본문을 직접 확인한 행만 점수에 포함한다.

### 다음 차수: 검사 전 재감사까지 고정한 표본

첫 차수의 오류 유형을 보고 코드를 고친 뒤, 다른 공개 글을 다시 고정했다. DVDPrime·퀘이사존 자료는 최초 라벨에 원문에 없는 정답 구간 1곳과 정상으로 잘못 표시한 문장들이 있어 **예측 전에** 원본을 보존하고 재감사판 SHA-256 `dde95a56c9693acd0e0f5376eda6fdb3913ce63d0c68b6497f88d8c39947e9c2`를 따로 잠갔다. 20발췌 중 근거가 불확실한 2행을 제외하고 18행·필수 교정 31곳을 평가했다. 첫 제안은 원문 범위 차이를 보정하면 18/31곳에서 정확한 대체안을 만들었고, 정상 3행에는 수정 오제안이 없었다. 라벨 밖 고유명사 `모아나를 → 모아 나를` 오제안 1곳을 추가 발견했다. 문장 전체를 첫 후보대로 바꾸면 교정 대상 15행 중 7행이 허용 본문과 일치했다. [DVDPrime 글 예](https://dvdprime.com/g2/bbs/board.php?bo_table=comm&wr_id=23466402), [퀘이사존 글 예](https://quasarzone.com/bbs/qf_cool/views/476106). 원래 라벨, 재감사 메모, 첫 예측, 검사기 실행 전후 해시는 Git 제외 `fresh-korean-2/`에 보존했다.

별도 영어 문법 자료 26발췌 중 Reddit 검색 발췌는 본문 URL을 직접 열어 확인할 수 없어 검증 점수에서 제외했다. 직접 페이지를 확인한 English Language Learners 14발췌는 오류 6곳 **첫 탐지 0/6**, 정상 8행 수정 오제안 0이었다. 이후 따로 고정한 같은 사이트의 다른 14발췌는 오류 7곳 **첫 탐지 0/7**, 정상 7행 중 `Did she have ...`의 `have`를 `has`로 바꾸려는 오제안 1행이었다. 합치면 직접 확인 오류 13곳에서 탐지 0곳이며 정상 15행 중 1행 오제안이다. 그 오제안의 조동사 문맥을 제한해 수정하고 같은 표본에서 오류 5/7 탐지·정확 구간 첫 후보 4/7을 얻었지만, 이는 개발 재실행이므로 첫 결과를 바꾸지 않는다. 입력 SHA와 첫 예측·감사는 `fresh-english-2/`에 보존했다. 영어 문법에 대해 독립 95% 목표를 충족하지 못했다.

### 지원 제공 순위표로 넓힌 커뮤니티

[다모앙 공개 글](https://damoang.net/)과 [일베 공개 글](https://www.ilbe.com/)을 직접 열어 본문 발췌의 출처를 확인했다. 원본 평가표를 검사 전에 보존하고, 출처 문구 불일치 1행과 판정 불확실성 2행을 검사 전에 제외했다. 검사 전 라벨상 13행에 필수 교정 8곳과 정상 5행이 있으며, 첫 실행은 **수정 후보 2/8**, 정확한 첫 후보 2/8, 정상 행의 수정 오제안 0/5였다. 이후 [국립국어원 답변](https://www.korean.go.kr/front/onlineQna/onlineQnaView.do?mn_id=216&pageIndex=1&qna_seq=320875&searchCondition=&searchKeyword=)에서 `좀더`도 허용됨을 확인했다. 따라서 이 1곳은 필수 교정 분모에서 빼야 하고, 사후 감사판은 **2/7**이다. 첫 라벨과 첫 결과는 수정하지 않았다. 유효한 나머지 오류 3곳은 대체안 없는 미등록 안내만 나왔고 2곳은 탐지하지 못했다. 정답표 밖의 정상 표현 `시민분들과`에는 불필요한 미등록 안내 1건이 있었다. 출처 URL 재확인, 제외 이유, 고정 입력·검사기 해시와 첫 예측은 Git 제외 `ranking-finance-social/`에 보존했다. 금융·직장 커뮤니티는 이번 차수에서 접근 제한 또는 본문 확인 실패로 평가하지 못했다.

[게임조선 밸런스토론장 사용자 글](https://www.gamechosun.co.kr/webzine/board/list.php?bid=balance) 11행은 수집 원본과 재감사판을 검사 전에 각각 SHA-256으로 고정했다. 필수 교정 15곳에서 첫 후보 정확 **4/15**, 필수 경계를 포함하지만 미판정 표현도 바꾸는 후보 1곳, 미등록 안내만 9곳, 무반응 1곳이었다. 정상 2행의 수정 오제안은 없었으나 `둠스데이`와 인명 일부에 불필요한 미등록 안내가 떴다. 같은 수집에서 확보한 기사 원문 15행은 사용자 문체 평가에 섞지 않았다. 첫 예측과 15곳 전수 감사는 Git 제외 `ranking-games-sports/`에 있다. 아카라이브·엠엘비파크 등의 접근 제한을 넘어서 수집하지 않았다.

[Home Assistant 커뮤니티](https://community.home-assistant.io/)·[Python 토론](https://discuss.python.org/)·[OPNsense 포럼](https://forum.opnsense.org/)의 직접 확인한 짧은 영어 발췌 35행도 검사 전 SHA-256 `7cb955597854a4dedc7c56048d948afb0cdb66b95c4eb756c786b2e5631f5fe8`로 잠갔다. 철자 중심 오류 20곳에서 원문 범위·첫 후보가 정확한 것은 **12/20**, 정확한 후보가 최대 5개 추천 목록 안에 있는 것은 14/20이었다. 정상으로 표시한 15행 중 3행에는 기술어 `rtmp`, `config`, `restreaming`, `duckdns`, `ints`의 잘못된 수정 제안이 있었다. 같은 `becuase` 오류가 여러 글에 반복돼 20곳은 12개 서로 다른 원문 오류 문자열에 불과하며, 이를 폭넓은 영어 문법 성능으로 확대하지 않는다. 잠긴 자료와 첫 예측은 Git 제외 `fresh-english-round3/`에 보존했다. 이 오제안과 후보 누락을 보고 코드를 고치는 재실행은 개발 점수로만 센다.

같은 수집자가 다른 원문에서 확보한 **영어 문법 16곳**은 검사 전에 별도로 고정했다(SHA-256 `383c46af231e13749670ee5cdda22ab5b416c072336050073ed83c06ec15a359`). 원문 맥락상 `for an example`은 뜻에 따라 허용될 수 있어 예측 전에 제외하고, 15곳으로 채점할 입력을 다시 잠갔다(SHA-256 `338f6b8defad0265d21008e6fc7af254f1f10e8223668e8f8ca0e9e4b8170bfc`). 당시 코드의 첫 실행은 **정확한 첫 후보 1/15**, 오류 범위와 겹치는 검출도 1/15였다. 수일치, 조동사 뒤 원형, 관사, 수량, 소유 대명사 등은 빠졌다. [Home Assistant 질문 예](https://community.home-assistant.io/t/automation-with-sun-condition-doesnt-works/175394)에서 발췌 맥락을 직접 확인했다. 이 실패를 보고 추가할 규칙의 같은 자료 재실행은 독립 점수로 쓰지 않는다.

### 추가 독립 4차: 다른 게시판의 사용자 문장

[보배드림](https://www.bobaedream.co.kr/board/bulletin/list.php?code=freeb)과 [알지롱](https://te31.com/rgr/) 사용자 글 15발췌를 새로 확보했다. 원본 13개 필수 구간 중 `먼길`의 결합 표기 허용 여부는 공식 근거를 확정하지 못해 **검사 실행 전에** 점수에서 제외했다. 채점 입력 SHA-256 `92ebff53be81b99febdc204b2d7403febc413b5f006d3e2641f34874d23cfbf8`의 오류 12곳에서 정확한 원문 범위·첫 후보는 **3/12**, 범위가 더 넓어도 필요한 수정만 한 `여수쪽으로 → 여수 쪽으로`를 포함하면 **4/12**였다. 정상 7행의 수정 오제안은 0건이다. 첫 예측과 검사기 해시, 사전 감사는 Git 제외 `ranking-round4-korean/`에 보존했다. 가생이·이토랜드는 수집 제한, NBA매니아·뽐뿌는 서버 제한, OKKY는 robots 확인 실패로 제외했다.

[Swift Forums](https://forums.swift.org/)·[Arduino Forum](https://forum.arduino.cc/)·[FreeBSD Forums](https://forums.freebsd.org/)에서 가져온 영어 28발췌도 직접 페이지와 원문 일치를 확인했다. 원본 SHA-256 `2c3764ac953a2c65dfd96a60ea6af718ef47d190ca334073f8cf36153f7f11c4`를 보존했다. `It it`의 잘못된 정답, 간접 의문문의 `how i can`에 잘못 적용한 도치, `in terminal`의 문맥상 불확실성을 **검사 전에** 제외한 채점 입력 SHA-256은 `ce23a467f63b239d04e9b6aad9dad21f582efa8d99e542b83ee5538e6bad8e35`다. 남은 오류 16곳에서 정확한 범위·첫 후보는 **7/16**, 오류 범위와 겹치는 제안은 9/16이었다. 정상 11행 중 2행의 `initializers`, `png`에 잘못된 수정 후보를 냈다. `sudo`, `pkg`, `yaml`도 확인된 기술어로 인식 목록에 보완했다. 같은 11행 재실행의 수정 오제안 0건은 **개발 결과**다. 첫 예측, 검사기 해시, 제외 사유는 `round4-english-diverse/`에 보존했다.

영어 문법 3차의 첫 평가 **1/15**를 본 뒤 수일치·조동사 뒤 원형 등 여섯 규칙군을 보완했다. 같은 표본의 엄격한 범위·첫 후보 일치는 11/15로 올랐지만 **노출된 개발 표본**이며, 4차 새 글의 7/16과 구분한다. `to this`, `What I am missing`, `a help`, `mine project`처럼 문맥 없는 자동 교정이 위험한 사례는 억지로 규칙화하지 않았다. 반복된 `becuase`를 포함해 각 차수는 작고 오류 위치를 선별한 부분 표본이다. 어느 차수도 독립 95% 완료 게이트나 문서 전체 정확도를 통과했다는 증거가 아니다.

영어 두 평가의 라벨·채점 정책과 검사기 파일 해시는 Git 제외 `local-corpora/live-2026-09-26/fresh-english/`에, DogDrip의 출처 확인과 첫 결과는 `fresh-korean/`에 보존했다. DogDrip 라벨 SHA-256은 `f7b91dce5a3858ed6215f374b8188aad851e8c2f00042a493902b635eadcdad0`다. 영어 표본도 첫 실행 전에 SHA-256으로 고정했다. 이 표본은 모든 문장 위치에 완전한 정답을 붙인 자료가 아니므로 문서 전체 정확도나 정상 글 오탐률로 확대할 수 없다.

DogDrip의 `www.dogdrip.net/dogdrip/...` 두 경로는 robots 허용과 10초 간격을 확인하고 읽었다. 같은 수집에서 뽐뿌 18발췌는 검색 결과에만 근거하며 원문 URL이 HTTP 403이어서 위 점수에서 제외했다. 네이트 판은 robots 차단, 에펨코리아 글은 HTTP 429에서 멈췄다. 이 첫 평가를 수집할 때는 지원의 순위표를 받기 전이었다. 사이트 이용자 나이의 확인 자료는 여전히 없어 문체가 다양한 공개 커뮤니티를 비교한 결과로만 해석한다.

첫 평가의 주요 실패는 한국어 `교회가야해서 → 교회가 야해서`, `아이등 → 아이 등`처럼 틀린 띄어쓰기 후보를 내는 일과 영어 `doesnt → doest`, 관사·수일치 누락이다. 기존 82cook·더쿠·루리웹·보배드림·오늘의유머 최초 라벨 88곳도 처음에는 29곳만 정확했다. 실패 59곳 중 명사·숫자·혼합어 경계가 28곳으로 가장 많았으며, 이 중 24곳은 정확한 후보를 만들지 못했다. 같은 사전에서 오류에 맞춰 규칙을 더해 점수를 올려도 독립 검증은 아니다. 현재 95% 완료 목표를 통과하지 못했다.

다섯 수집 경로의 표본은 **사이트 이용자 연령 분포를 증명하지 않는다.** 이 묶음을 수집할 당시 순위표는 아직 받지 않았으므로 순위별 대표성도 주장하지 않는다. 이후 받은 순위표를 사용한 표본은 별도 차수로 보관한다. 클리앙·디시인사이드 후속 접근은 AI 수집 제한을 확인하고 제외했다. 뽐뿌·인스티즈는 403/접근 도전, 네이트 판·웃긴대학·SLR클럽은 robots 제한으로 제외했다. 오늘의유머와 더쿠는 robots 파일이 404였고 공개 페이지가 열렸다는 사실만 기록한다. 원문 전체, 작성자 식별정보, 댓글 계정, 이미지는 보관하지 않았다.

노출된 표본에서 `남아돈다는게 → 남아돈다는 게`, `안돼고 → 안 되고`, `결혼하고나서 → 결혼하고 나서`, `살고싶엇다 → 살고 싶었다` 등의 결함을 고쳤다. 같은 구간을 재실행한 결과는 개발 확인에만 사용한다. `-ㄹ 뻔하다`는 붙여 쓰는 형태도 허용되므로 이를 필수 오류로 고치지 않았다. 이 근거 확인으로 초기 `집어올뻔했다`의 뻔 앞 공백을 필수 교정으로 삼은 판정은 보류한다.

승인받은 격리 비교에서 `harper.js@2.10.0`을 제품 밖 임시 환경에 설치했다. 감사한 영어 8곳은 기존 검사기 2곳, Harper 3곳, 합친 후보 3곳만 일치했다. 이전 영어 25곳도 기존 9곳, Harper 5곳, 합친 후보 10곳이었다. `quite → quiet`, `Etihad → Ethan`, `Chargeback → Chargeable`, `Nextflow → Netflix` 같은 정상어 오제안이 있었다. WASM은 원본 약 16.16MB, gzip 약 8.13MB였고 Node 첫 준비 약 575ms, 32구간 검사 약 396ms였다. 표본과 환경이 제한적이지만 품질과 크기 모두 이득을 입증하지 못해 제품 의존성에 추가하지 않았다. 이 비교 결과로 기존 영어 검사기의 전체 문법 품질이 충분하다는 뜻도 아니다.

지원이 승인한 별도 [MeCab 한국어 사전](https://github.com/LuminosoInsight/mecab-ko-dic) 비용표 실험은 제품 밖에서 수행했다. 고정된 한국어 64행·오류 88곳 중 공백 삽입 오류 67곳에 비용표 후보를 적용하면 기존 첫 결과 24/67에 비해 비용 조건을 켠 단순 후보는 32/67을 맞혔다. 그러나 정답 표시가 없는 정상 표현 66어절 중 15어절도 분리하려 했다(`에피큐리언 → 에피 큐 리언`, `신뢰도와 → 신뢰도 와`). 가공 비용 자료 gzip 합은 5.98MB이고 Node 프로세스 RSS는 초기 약 448MiB, 실행 뒤 약 539MiB였다. 현재 검사기와 수행 범위가 달라 1만 자 속도 수치를 제품 비교로 사용하지 않는다. 정상 표현을 지키지 못하므로 비용표를 제품 자산이나 코드에 채택하지 않았다. 원본 리비전·해시·실험 스크립트·수치는 Git 제외 `mecab-cost-pilot/report.md`에 보존했다.

접근이 허용된 공개 게시글을 읽고, 각 차수의 정답 구간·대체 문구를 **검사기 첫 실행 전에** 비공개 `local-corpora/live-2026-09-26/*-labels.json`에 고정했다. 동일 폴더의 `*-first-predictions.json`이 첫 결과다. 각 차수의 실패를 고친 뒤 그 차수의 재실행은 개발 결과이며 아래 첫 결과를 덮지 않는다. 평가표는 명시한 오류 구간만 판정했고 다른 구간은 미판정이다.

각 차수 사이에 검사기 코드가 바뀌었다. 이 숫자를 합쳐서 현 버전의 정확도라고 표현할 수 없다. 예를 들어 5차 영어 첫 평가는 0/10이었고 해당 10곳에 대응하는 규칙을 추가한 재실행은 8/10이지만, 그것은 새 자료에 대한 독립 통과가 아니다. 6~8차의 명시 오류도 현재 코드의 다음 개발 입력이 됐다. 최초 평가는 모두 원문 그대로 보존한다.

이전 차수에서는 이 출처들의 공개 페이지를 실제로 읽었다: [디시인사이드 기계식키보드 갤러리](https://gall.dcinside.com/mgallery/board/lists/?id=mechanicalkeyboard), [루리웹 게시글 예](https://bbs.ruliweb.com/community/board/300143/read/76811951), [인벤 구 게시판 예](https://www.inven.co.kr/board/lostark/4811/9358033), [인벤 현 게시판 예](https://www.inven.co.kr/board/lostark/6271/4139601), [Hacker News 토론 예](https://news.ycombinator.com/item?id=49840054). 로그인 없이 공개 글만 읽었고 외부 글이나 댓글을 쓰지 않았다. Hacker News의 robots.txt에 적힌 30초 간격을 확인했으며, 초기 목록 확인 2회는 이보다 가까웠다. 이후 본문 수집에서는 요청 간격을 두었다. 당시 클리앙·뽐뿌·DogDrip의 확인한 경로에서는 접근 제한으로 본문을 수집하지 않았다. 뒤의 별도 수집에서는 DogDrip의 허용된 `www` 공개 글 경로를 찾아 읽었고, 뽐뿌는 HTTP 403으로 원문을 읽지 못했다. 에펨코리아는 목록이 열렸지만 게시글 경로가 차단되어 본문을 읽지 않았다. 디시인사이드는 후속 목록에서 본문 없는 응답이 나타난 뒤 요청을 멈췄다.

평가의 한계가 크다. 정상 문장 200개의 **전체 판정**과 오제안률, 미등록 항목 95% 검토율, 첫 후보 98% 및 필수 교정 95%를 검증하지 못했다. 언어별로 노출된 개발 사례를 계속 메우면 재실행 점수는 오르지만, 새 글에서는 같은 비율이 유지되지 않았다. 인벤 6차에서 관리자 공지 두 건은 HTML 본문의 문단 경계가 무너져 첫 실행 전 제외했다. 나머지 글도 원문 추출과 사람 판정에 오류가 있을 수 있다.

판정 감사도 첫 결과와 분리한다. 2차의 `사놓은 거`는 [국립국어원 답변](https://m.korean.go.kr/front/onlineQna/onlineQnaView.do?mn_id=216&pageIndex=1&qna_seq=314531)에 따라 허용되는 붙임 형태다. 6차의 `세네 개` 단일 대체 표기는 [국립국어원 설명](https://www.korean.go.kr/front/onlineQna/onlineQnaView.do?mn_id=216&qna_seq=309796)에 비추어 표준어 `서너 개`와 구어체 보존을 구분하지 못했다. 두 평가표를 사후 수정하지 않고 해석에 주의를 단다. 하나의 평가 구간에 철자와 띄어쓰기 두 오류가 포함된 경우, 검사기의 별도 제안 두 개는 이 일치 계산에서 누락으로 남을 수 있다.

6차 영어 `important bit → important bits` 표시는 이미 맞는 `important bits` 안의 부분 문자열을 잘못 가리켰으므로 무효다. `Absolute love → Absolutely love`는 구어체 표현의 허용 범위가 불명확하고 `agents own discovery`의 소유격 해석도 문맥 의존적이다. 이 항목들로 6차 성공률을 높이거나 낮추는 재계산은 하지 않는다. 검사기와 별도로 진행한 Luna의 한영 3역할 비교는 공개 글 4개에 12/12회 완료했다. 몇몇 놓친 오류를 찾았지만 정상적인 `it's basically useless`를 `its`로 바꾸는 오교정도 냈다. 모델 출력을 자동 정답이나 독립 합격 증거로 쓰지 않는다.

현재 UI에 넣은 영어 문법 제안은 근거가 분명한 일부 구문만 다룬다. 현행 제품 문구도 영어 문법 전체를 보장하지 않도록 고쳤다. 독립 완료 게이트가 실패했으므로 이슈 #6을 완료로 판정하거나 닫을 근거는 없다.

공식 `node scripts/eval-spelling.mjs --engine scripts/spelling-prototype.mjs`를 최신 코드에서 실행했다. 저장소의 자체 작성 200사례는 `Independent evaluation: false`라고 출력한다. 전체 한국어 철자 24/25, 띄어쓰기 34/35, 영어 철자 28/30, 한국어 정상 30/30, 영어 정상 15/15였다. 초기 한국어 holdout 게이트는 탐지 18/20·정상 오추천 0으로 PASS다. 그러나 영어 철자 사례에서 잘못된 후보가 14개였고, 이 자료는 개발에 노출된 자체 사례다. 공개 글의 첫 평가를 대체하지 못한다.

다음 구조 검토 대상으로 [Harper의 `harper.js`](https://github.com/Automattic/harper)를 확인했다. 공식 설명에 따르면 Apache-2.0이며 WebAssembly로 기기 안에서 영어 철자·문법을 검사한다. [JavaScript 문서](https://writewithharper.com/docs/harperjs/linting)는 브라우저 Worker 사용을 권한다. 한국어는 지원하지 않으며 Wonboard 원문의 문체·약칭 보존율도 아직 측정하지 않았다. [LanguageTool의 지원 언어 목록](https://help.languagetool.org/hc/en-us/articles/39254526141463-What-languages-does-LanguageTool-support)에 한국어는 없고 코어 라이선스도 LGPL이므로 현 제품 정책의 즉시 대안으로 보지 않는다. [GeulLint](https://github.com/binibinibin123/geullint)는 로컬 한국어 검사 MIT 베타지만 자체 안내에 범용 미등록어 후보와 독립 정밀도 근거의 한계가 명시돼 있다. 어떤 것도 새 의존성으로 추가하거나 제품에 넣지 않았다.

8차 영어 원문은 [Hacker News 토론](https://news.ycombinator.com/item?id=49849985)의 수집된 본문 중 페이지 순서 앞 30개를 사용했다. 평가표를 검사기 실행 전에 고정했다. `half-skilled` 같은 하이픈은 필수 교정인지 불분명하므로 해석에 주의해야 한다.

9차는 [루리웹 게시글](https://bbs.ruliweb.com/community/board/300143/read/76812613)과 [다른 주제의 Hacker News 토론](https://news.ycombinator.com/item?id=49852717)으로 구성했다. 영어 명시 오류가 4개뿐이라 그 비율만으로 영어 성능을 일반화할 수 없다. 판정하지 않은 정상 표현에서도 `non-stop`, `a priori`, `async`, `Lego`를 다른 단어로 바꾸는 후보를 확인했다. 이 항목들은 공통 인식 어휘에 추가했으나 같은 글의 재평가는 독립 표본이 아니다.

10차는 [인벤 게시판 4페이지](https://www.inven.co.kr/board/lostark/6271?p=4)와 [Hacker News 토론](https://news.ycombinator.com/item?id=49852302)을 사용했다. 영어 HTML 추출에서 연속된 문단 사이 공백이 지워진 곳은 원문 오류로 표시하지 않았다. 영어 관사의 명백한 오류 두 사례를 수정한 같은 자료 재실행은 2/10이며, 첫 결과 0/10은 그대로 보존한다. 한국어에서는 `안써야하는거`, `일정조율이였음`처럼 여러 오류가 한 어절에 결합되면 제안이 없었다. 같은 어절의 부분 교정만 나온 경우에도 전체 문자열 일치 게이트는 누락으로 센다.

10차의 명시 오류 밖에서도 정상적인 게임 직업 이름 `도화가랑`을 `도화 가랑`으로, 인명 `Ayn`을 `Any`로, 기술 약칭 `rss`를 다른 영어 단어로 바꾸려는 후보가 나왔다. `re-add`, `woulda`, `dem`, `클영상`도 문맥상 쓰인 표현으로 판정해 인식만 추가했다. 첫 결과의 오교정 기록은 그대로 두며, 이 단어 목록을 개발에 사용했으므로 같은 글에서 오교정이 사라졌다는 사실은 독립 정확도 근거가 아니다.

11차는 코드를 고친 뒤 새로 읽은 [인벤 게시판 5페이지](https://www.inven.co.kr/board/lostark/6271?p=5)와 [Excel 기능 관련 Hacker News 토론](https://news.ycombinator.com/item?id=49849832)이다. 평가표를 실행 전 SHA-256 `6f2d6ee10c66…`으로 고정했다. 첫 결과는 한국어 20/51, 영어 2/15다. `its been`, `to treated as`, `make it sounds` 같은 공통 영어 구문을 추가한 같은 자료 재실행은 7/15다. 한국어 `신고넣엇음`처럼 문맥과 복수 오류를 함께 처리해야 하는 항목이 남았다. 이 수치는 10차 어휘 보완이 새 글의 필수 오류 회수율을 높였다는 근거를 주지 않는다.

11차의 정상 표현을 잘못 바꾸는 후보 중에는 `할모시`, `클리어임`, `non-programmers`, `SPSS`, `numpy`, `coursework`, `xlookup`, `multivalue`, `scrollbars`, 영국식 `normalisation`이 있었다. 원문에서 의도한 단어로 판정해 인식만 추가했다. 긴 어미를 끊어 `떨려와요오 → 떨려와 요오`로 제안하는 오교정은 남았다. 이처럼 명시 오류 회수율과 정상 표현 보존율 모두 독립 평가가 부족하다.

Chrome 154 Worker에서 공개 글을 1만 자로 맞춰 5회씩 검사했다. 첫 로드 1,186.5ms, 한국어 중앙값/최댓값 44.3/73.9ms, 영어 12.9/17.7ms, 혼용 18.1/18.8ms였다. 이 자료는 반복되도록 이어 붙였으므로 문장 분포가 새 글 1만 자와 같다는 뜻은 아니다. 별도의 공백 없는 64음절 낯선 어절 반복은 2초 기준을 넘어, 48자를 넘는 단일 어절을 대체 제안 없이 검토 항목으로 표시했다. 같은 Chrome에서 재측정한 이 병적 입력의 중앙값/최댓값은 2.6/2.8ms였다. 전체 문서 길이 제한은 두지 않았다. UI 입력 반응, 취소 시간, 비교 기준 빌드와의 성능 차이는 이 측정으로 증명되지 않는다.

11차 당시 빌드의 `review.worker`는 웹·데스크톱에서 동일하게 6,642,486바이트, gzip 1,861,596바이트다. 입력 자료 `lexicon.json`은 원본 2,810,026바이트/gzip 661,311바이트, `morphology.json`은 원본 4,679,129바이트/gzip 1,198,134바이트다. gzip은 동일 파일에 `compresslevel=9`로 적용한 값이다. Worker에는 두 자료가 포함되므로 세 압축 크기를 합쳐 전송량이라고 보지 않는다. 이 시점에는 기존 빌드와 같은 조건의 크기·첫 로드·메모리 비교가 없었다.

11차 수정 후 Vitest 241건과 Node 단위 시험 372건, 타입 검사, Sites·데스크톱 빌드가 통과했다. Chrome 맞춤법 UI 전체 시험은 135/137건 통과했고, 실행 중 코드 갱신과 겹친 한국어 2건이 실패했다. 코드를 더 바꾸지 않고 그 두 사례를 다시 실행해 2/2건 통과했다. 전체 137건을 한 번에 재실행해 모두 통과시킨 기록은 없다. 설치된 macOS 앱, Windows 실기기, 실제 한글 IME, UI 입력 지연·취소 응답은 별도 미확인이다.

## 최종 로컬 실행과 완료 판정

마지막 어휘 보완을 포함한 검사기에서 Vitest 241건, Node 단위 시험 380건, `pnpm typecheck`, `pnpm build:sites`, `pnpm build:desktop`와 데이터 정책 검사가 통과했다. 최종 어휘 보완을 포함한 코드에서 Chrome 맞춤법 E2E 전체 137건이 한 번에 통과했다(4.1분). 격리된 macOS Electron 빌드에서는 한국어 네 사례와 영어 문법 `There is many users.`, `They seems ready.`의 후보 선택·바꾸기·undo/redo·저장, 프로세스 재실행 후 개인 사전 유지·삭제를 확인했다. 이것은 지원의 기존 설치 앱을 교체한 결과가 아니다.

공식 `node scripts/eval-spelling.mjs --engine scripts/spelling-prototype.mjs` 출력은 `Cases: 200. Independent evaluation: false`다. 한국어 철자 24/25, 띄어쓰기 34/35, 영어 철자 28/30, 정상 한국어 30/30, 정상 영어 15/15이며 영어 철자에서 잘못된 부후보 14개가 나온다. 이 자체 작성 자료에는 영어 문법 95% 검증이 없다. 위 공개 글의 새 첫 평가 성적과 정상어 오제안도 완료 게이트를 통과하지 못했다.

macOS 27 ARM64의 Headless Chrome 153에서 같은 스크립트와 1만 자 반복 입력을 기존 main 빌드와 최종 Worker에 각각 5회 적용했다. 최종 첫 검사 로드 1,346.1ms(기존 1,323.9ms), 일반 한국어 중앙값/최댓값 21.5/30.1ms(기존 17.5/22.2ms), 오류 한국어 42.6/51.4ms(기존 35.0/45.1ms), 영어 오류 49.7/58.7ms(기존 40.4/46.2ms), 합성 미등록어 334.8/386.9ms(기존 330.1/390.9ms)였다. 긴 미등록어 반복은 2.7/3.0ms이며 기존 2,165.5/2,333.4ms의 병적 지연은 앞선 길이 제한 수정으로 해소됐다. 이 입력에서 반복 검사 최댓값은 목표 500ms 미만이다. 주 스레드 타이머 지연 대리 지표는 최대 0.1ms, Worker 종료 후 550ms 동안 늦은 응답은 0건이었지만, 실제 키 입력·한글 OS IME·저사양 기기 반응이나 Worker 메모리를 직접 증명하지 않는다.

최종 Sites·데스크톱의 동일한 `review.worker`는 원본 6,654,277바이트, gzip 1,865,617바이트, SHA-256 `b75e965a14719adac89ecb155eda200a5f88cdfb4450f88ffd6bd51e35fcb0f3`다. `lexicon.json`은 원본 2,810,026/gzip 661,311바이트, `morphology.json`은 원본 4,679,129/gzip 1,198,134바이트다. 두 JSON은 Worker에 포함되므로 gzip 값을 합산해 추가 전송량이라고 하지 않는다. 크기 고정 상한은 적용하지 않는다.

독립 필수 교정 목표 95%와 정상문 보존, 완전 판정된 200개 오류·200개 정상문 게이트는 여전히 미달이다. 이슈 #6을 닫거나 기존 설치 앱을 이 빌드로 교체하지 않는다. 모델·런타임을 새로 넣는 방안은 별도 라이선스·자료·성능 판단이 필요하며 이번 제품 빌드에는 포함되지 않았다. Windows 실기기와 실제 OS 한글 IME는 미확인이다.
