## 1. 목표와 현재 상태

### 추가 필수 범위: 맞춤법·사진 부하·실제 저장소 연결

지원의 추가 요청에 따라 다음 세 항목을 클라이언트 완료 기준에 포함한다. 아래는 구현 요구사항과 검증 계획이며, 새 검사 엔진 도입·부하 측정·외부 계정 연결을 완료했다는 뜻이 아니다.

**AI 없는 맞춤법 검사.** 현재 제목과 본문은 브라우저 `spellcheck`를 켰지만 언어별 동작은 브라우저/OS 설정에 의존한다. 원보드가 제공하는 한영 검사 UI에는 오류 표시, 수정 후보, 이번만 무시, 사용자 사전, 실행 취소를 포함한다. 문장을 자동으로 바꾸지 않으며 한글 조합 중에는 검사와 교체를 보류한다. 코드·URL을 제외하고 한영 혼용, 고유명사, 숫자를 검증한다. 외부 AI/API로 원문을 보내지 않는 자체 검사 경로를 목표로 한다. 브라우저 자체의 향상된 검사 설정까지 원보드가 통제한다고 약속하지 않는다.

한국어 후보는 [Hunspell 한국어 사전](https://github.com/spellcheck-ko/hunspell-dict-ko)이다. 단어 단위 검사와 문맥에 따른 띄어쓰기/문법 검사를 구분한다. 해당 프로젝트는 전체 결과물을 GPL-3.0으로 안내하고 데이터별 라이선스도 다르므로, 엔진·사전의 정확한 배포 파일과 의무를 확인하고 도입 승인을 받은 뒤 통합한다. 원보드의 MIT 코드를 이유로 사전까지 MIT로 표기하지 않는다. 엔진 선택 전에 작은 한영 정답/오답 자료로 검출률·오탐·수정 후보·한글 위치 매핑·실행 속도를 검증한다.

지원이 제안한 [toss/es-hangul](https://github.com/toss/es-hangul)의 공식 문서와 공개 export를 확인했다. MIT 한글 문자열 처리 라이브러리로, 초성 검색·자모 분해/조합·조사 선택 등에 활용할 수 있다. 원보드에서는 문서 목록 초성 검색과 자연스러운 한국어 UI 문구를 위한 후보로 둔다. 단어 사전·오류 판단·문맥 맞춤법 검사기를 제공하는 것으로 취급하지 않으며 Hunspell 대체재로 확정하지 않는다. 현재는 검토만 했고 의존성을 설치하지 않았다.

**사진 부하 측정.** 코드의 현 상한은 문서당 100장, 장당 20 MiB, 4천만 화소, ZIP 백업 256 MiB다. 이는 실측한 안전 용량이 아니다. 기존 50장 시험은 120×80 이미지로 순서와 복원을 확인한 것이며 실사진 부하 시험이 아니다. 특히 허용되는 문서의 원본 총량이 ZIP 상한을 넘을 수 있어, 백업 가능한 문서 한계를 별도로 확인해야 한다.

- 사용자 브라우저와 초안을 건드리지 않는 격리된 브라우저·합성 이미지·전용 임시 폴더로 측정한다. 외부 업로드 없이 먼저 실행할 수 있다.
- PNG 캡처형과 JPEG 사진형을 나누고 파일 크기·해상도·장수를 각각 기록한다. 10→25→50→100장, 원본 합계 25→100→250 MiB 순으로 단계적으로 올린다. 실제 생성된 바이트와 화소 수를 기록하고, 상한 이상은 거부/복구 시험으로 구분한다. 기본 제품 상한을 몰래 늘려 시험하지 않는다.
- 삽입, 자동 저장, 글자 입력 지연, 스크롤, 문서 전환, 새로고침, 미리보기, ZIP 생성/복원 시간을 각각 측정한다. 여러 문서에 사진이 누적되는 경우도 포함한다. 측정 가능한 브라우저/프로세스 메모리와 저장 용량을 구분하며 JS 힙만으로 전체 이미지 메모리를 대표하지 않는다.
- Chromium/Firefox/WebKit에서 동일 자료를 사용한다. 단계별 3회 측정하고, 시험 환경과 관측 최댓값을 남긴다. 입력 반영 p95 100ms 이내를 초기 사용성 목표로 삼되 실제 도구가 측정한 범위를 명시한다.
- 원본 해시·이미지 순서·크기·설명·문서 내용의 왕복 보존은 전수 일치해야 한다. 한 건의 손상, 탭 종료, 10초 이상 무응답 또는 한 단계 120초 초과 시 추가 증량을 중단하고 실패 지점을 기록한다. 사용자의 컴퓨터 전체를 메모리 부족까지 밀어붙이지 않는다.
- 실패 직전 장수를 제품 권장 한도로 발표하지 않는다. 반복 통과한 장수·총용량·해상도와 여유를 함께 보고하고, 병목을 수정한 뒤 동일 자료로 다시 측정한다.

**실제 저장소 연결.** 로컬 부하 검증과 별개로 실제 업로드와 외부 게시판 표시까지 클라이언트 완료 범위에 포함한다. 지원이 첫 제공자로 **Google Drive**를 선택했다. 익숙한 Google 계정으로 시작하는 작성자의 접근성을 우선하며, Cloudflare 계정을 선행 조건으로 요구하지 않는다. R2는 후속 제공자로 둔다. Drive를 백업 전용으로 축소하지 않고 문서·이미지 저장/복원과 외부 게시용 이미지 전달 가능성을 함께 구현·검증한다.

지원은 게시글을 5년 뒤에 열어도 동일한 사진을 볼 수 있어야 한다고 명시했다. 게시용 URL 자체에 시간 만료를 두지 않고, 비활동·제목 변경·로그아웃·토큰 갱신·저장소 이동 때문에 기존 게시글의 주소가 바뀌거나 이미지가 삭제되지 않는 것을 설계 기준으로 삼는다. URL의 무기한 유효성과 서비스/도메인/원본의 지속 운영은 별개다. 운영 조건과 보존 정책을 명시하고, 게시용 이미지 및 URL 매핑 백업을 복원하거나 저장소를 이전한 뒤에도 기존 URL로 동일한 이미지가 나오는지 시험한다. 실제 5년 보존 실적이나 제3자 영구 보증이 있다고 주장하지 않는다.

Drive 공개 이미지 한 장의 비로그인 접근 시험은 지원이 승인했다. Chrome 파일 선택 도구의 거부 후 지원이 같은 테스트 PNG를 `download.png`로 직접 업로드했다. 파일 ID는 `18k9PfRHDZlpnvbjmeEKRD9e1MllFrGfg`다. 최초에는 '나에게만 공개'였고 인증 없는 HTTP 요청은 401이었다. 승인된 테스트 파일 한 장만 '링크가 있는 모든 사용자 / 뷰어'로 변경했고 저장 완료를 확인했다. 다른 파일은 변경하지 않았다. Google Cloud 프로젝트/OAuth 앱은 아직 생성하지 않았다.

2026-09-05 실제 검증 결과: 공개 후 인증/쿠키 없는 Node fetch로 공유 화면은 HTTP 200 HTML, 그 화면이 제공하는 다운로드 주소는 HTTP 200 `image/png`를 받았다. 원본 640×360, 3,554바이트이며 SHA-256 `05b88f941fb3598eef57975c9de1847bd9128a899c4c8f04c03b69f262950cfe`가 로컬 테스트 원본과 일치했다. 다운로드 응답의 `Content-Disposition`은 attachment, `Cross-Origin-Resource-Policy`는 same-site, `Cache-Control`은 private/max-age=0이었다. 공유 화면의 파일 ID 기반 다운로드 경로를 사용했으며 임시 viewer 이미지 주소를 게시용으로 채택하지 않았다.

별도 loopback 시험 페이지(4181 포트, 기존 5173 작성기/초안과 분리)에서 동일 다운로드 주소를 `<img>`에 직접 넣자 Chrome에서 표시 실패했다. CDP가 기록한 실제 오류는 `net::ERR_BLOCKED_BY_ORB`였다. 반면 로컬 시험 서버가 인증 없이 동일 원본을 받아 해시 검증 후 `image/png`로 전달한 경우 Chrome에서 640×360 표시 성공을 확인했다. 이 결과는 **Drive 원본 + 원보드 전달 서버** 구조의 소규모 기술 가능성을 증명한다. 다른 모든 Drive URL 방식이 불가능하다는 증명, 실제 PGR 게시 성공, 부하/할당량 검증, 비공개 OAuth 연동, 공개 서버 배포, 5년 보존 보증은 아니다. 실제 전달 서버의 고정 HTTPS 주소·보존/백업·장애 대응은 아직 구현하지 않았다. 테스트 파일은 추가 시험을 위해 공개 상태로 남긴다.

Drive 연결은 기존 1인 테스트 로그인과 별도로 첨부 탭의 연결 버튼에서 시작한다. 기본 권한은 앱에서 만든 파일 또는 사용자가 앱에 선택해 준 파일만 접근하는 `drive.file`로 설계한다. 문서/원본은 비공개로 보관하고 게시용 파생본 공개는 명시적 게시 준비 동작에서 구분한다. 승인받지 않은 기존 Drive 파일을 조사하거나 권한을 넓히지 않는다. 업로드·재시도·다시 열기·연결 해제·토큰 만료·할당량 초과를 검증하며, 연결 해제는 파일 삭제로 해석하지 않는다.

Drive의 `webViewLink`는 보기 링크, `webContentLink`는 다운로드 링크이며, `thumbnailLink`는 단기 링크다. 임의 URL 변형만으로 외부 게시판용 영구 주소가 확보됐다고 판단하지 않는다. 별도 인증 없는 브라우저와 PGR에서 이미지 접근을 먼저 시험하고, 직접 전달이 요구를 만족하지 못하면 원보드 서버의 공개 이미지 전달 경로 필요성을 근거와 함께 제안한다. 서버 운영이나 캐시 비용은 별도 결정이며 R2 사용을 몰래 선행 조건으로 추가하지 않는다.

현재 저장소에서 Google OAuth 앱 ID/시크릿 설정이 없는 것을 확인했다(값은 출력하지 않음). 실제 계정 연결에는 사용할 Google Cloud 프로젝트, Drive API 활성화, 웹 OAuth 클라이언트와 정확한 리디렉션 주소 설정이 필요하다. 기존 프로젝트 선택 또는 새 프로젝트/앱 생성은 지원의 승인을 받은 뒤 진행한다. [Drive 최소 권한 문서](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)를 따른다.

- 첨부 탭에서 연결 상태, 용도(비공개 원본/공개 게시용), 업로드 대기/진행/실패를 구분한다. 저장소 연결은 소셜 로그인 도입과 별개다.
- 임시저장은 계속 로컬로 처리한다. 게시 준비 시 파생 이미지 변환·제목 기반 이름 정리·업로드·공개 URL 확인을 수행한다. 실패한 항목만 재시도하고 새로고침 후 중복 업로드 여부를 확인한다.
- 비공개 초안/원본을 공개 이미지 영역에 자동 업로드하지 않는다. URL은 인증 없는 새 브라우저에서 이미지로 직접 열려야 하며, 만료되는 업로드용 URL을 본문에 넣지 않는다.
- 제목 수정 시 새 게시용 이름은 따라 바뀌되 이미 외부 글이 참조하는 URL을 삭제하거나 깨뜨리지 않는다. 기존 게시 버전과 새 게시 준비 버전을 구분한다.
- 네트워크 단절, 일부 성공, 인증 만료, 용량 부족, 재시도, 로그인하지 않은 외부 독자의 이미지 접근을 실제 연결에서 검증한다. 정상 업로드 한 번만으로 완료 처리하지 않는다.
- 계정·버킷/폴더·도메인·공개 범위·비용 상한·시험 파일 삭제 범위를 확인하기 전 외부 리소스 생성, 공개 설정 변경, 유료 부하 시험, 배포를 하지 않는다. 현재 로컬 테스트용 로그인 서버를 인터넷에 그대로 노출하지 않는다.

연결 설계는 [Cloudflare R2 공개 버킷](https://developers.cloudflare.com/r2/buckets/public-buckets/)과 [Google Drive 파일 필드](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)를 기준으로 확인했다. Drive의 보기/다운로드 링크를 게시판용 영구 이미지 주소와 동일하게 취급하지 않는다. 계획만 반영했으며 계정 연결·라이브 부하 시험은 아직 수행하지 않았다.

Wonboard는 사람이 직접 글을 쓰는 웹 워드프로세서와, 그 문서를 온전히 받아주는 설치형 게시판 서버를 함께 제공한다. 완성한 글의 목적지는 작성자가 선택한다. 에이전트는 홈페이지 구축 과정에서 Wonboard를 쉽게 선택·설치·변경할 수 있어야 한다.

- 공개 저장소: https://github.com/jiwonschol/wonboard
- 원격 초기 커밋: `c5b7d33`. 그 이후 로컬 작성기와 공통 패키지를 구현했다. 이번 변경은 아직 커밋·push하지 않았다.
- 한 모노레포 안에서 클라이언트와 서버를 분리한다.
- Onsoon Labs 홈페이지에도 소개 링크를 넘어 실제 편집기·게시판을 연결할 수 있게 한다. 기존 홈페이지 저장소는 아직 조사하거나 변경하지 않았다.
- 이 문서는 최초 브리프 이후 대화에서 바뀐 결정을 반영한다. 최초 브리프의 AI 초안 편집 중심 사례는 현재 구현 범위가 아니다.

## 2. 사용자 확정 결정

1. 클라이언트는 웹으로 구현한다. macOS 전용 앱을 먼저 만들지 않는다.
2. 사람이 제목·본문·서식을 작성하고, 캡처를 붙이거나 사진을 드래그해 원하는 문단 사이에 넣는다.
3. 사진 크기를 드래그로 조절하고 그 표시 의도를 저장한다.
4. 작성 중 원본 사진과 문서는 브라우저에 보관한다. 임시저장마다 원본을 클라우드에 업로드하지 않는다.
5. 게시 준비를 위한 저장 시 사진의 형식·크기·파일명을 정리하고 사용자가 연결한 저장소에 공개용 파일을 업로드한다.
6. 공개 주소가 포함된 본문을 목적지에 맞춰 내보낸다. 직접 게시 연동이 없어도 붙여넣기가 유용해야 한다.
7. Wonboard Server는 같은 문서와 작성 경험을 지원한다.
8. 한국식 게시판과 Reddit식 토론 게시판 등을 포함해 5~10개 프리셋을 제공한다. 구현 순서를 나누되 최종 범위에서 제거하지 않는다.
9. 초기에는 `admin` 한 명이 비밀번호로 로그인해서 테스트한다. 회원가입·소셜 로그인·다중 사용자 운영 UI는 이후 단계다.
10. 한국어와 영어를 처음부터 지원한다.
11. 초기 디자인은 지원이 열어 준 WordPress Playground 편집 화면을 충실하게 재현한다. 임의의 새 시안이나 다른 서비스 화면으로 대체하지 않는다.
12. AI 글쓰기 기능과 자체 AI 구독은 필수가 아니다. API·CLI·MCP는 게시판의 설치·설정·연결·운영을 위한 인터페이스다.
13. 향후 외부 사이트에서 소수의 실제 게시·확인·삭제 테스트를 진행한다. 계정 가입은 지원이 담당한다.
14. Wonboard 자체 코드는 MIT 라이선스로 공개한다. 지원이 상업적 사용·비공개 수정본 배포 허용을 확인했다.

### 라이선스 결정

- Wonboard 자체 코드는 MIT로 결정했다. 상업적 사용과 비공개 수정본 배포 허용을 지원이 승인했다.
- 루트 LICENSE 파일을 로컬에 추가했다. 아직 원격 저장소에는 올리지 않았다.
- Tiptap의 오픈소스와 유료 기능의 경계를 의존성별로 검사한다.
- WordPress 화면 재현과 Gutenberg 코드 재사용은 별도 결정이다. 이번 추천은 Tiptap 위에 화면을 직접 구현하는 방식이다.
- Gutenberg 소스·스타일·아이콘·폰트를 가져와야 한다면 각 자산과 패키지의 라이선스를 확인한다. WordPress 프로젝트 전체가 MIT라고 취급하지 않는다.
- 독자 구현이 승인된 화면·입력 경험을 만족하지 못한다면 변경 근거와 함께 재사용 선택을 다시 제안한다. 원본을 임의로 단순화해 성공으로 처리하지 않는다.

## 4. 모노레포와 홈페이지 연결

```text
apps/
  client/                  작성기·문서 목록·브라우저 보관
  server/                  API·세션·게시판·관리·DB·공개 글 서빙
packages/
  document/                문서 스키마·검증·버전 변환
  editor/                  다른 홈페이지에서도 쓰는 React 작성기
  renderer/                본문 표시·안전한 HTML 생성·본문 스타일
  publishing/              목적지별 변환·호환성 진단
  locales/                 ko/en 공통 문구
examples/
  embedded-editor/         외부 홈페이지가 실제 편집기를 사용하는 예제
docs/
  planning/
  architecture/
  integration/
  compatibility/
```

스토리지와 인증은 각 앱 내부에서 시작한다. 두 번째 실제 사용처가 생기기 전에는 불필요한 패키지로 분할하지 않는다. 공통 패키지는 다른 앱의 내부 파일을 import하지 않는다.

에디터 패키지는 `document`, `locale`, `readOnly`, 미디어 삽입 처리, 변경 알림 같은 공개 입력·콜백을 제공한다. 저장소 비밀번호·admin 세션을 에디터에 묶지 않는다. 실제 인터페이스는 M0에서 타입으로 고정한다.

Onsoon Labs 연결은 먼저 이 저장소의 예제 호스트에서 검증한다. 기존 홈페이지의 프레임워크·배포 방식·인증 구조를 확인한 뒤 통합한다. React 패키지 방식이 맞지 않으면 별도 선택을 제안한다. 처음부터 임의의 원격 스크립트 실행 기능이나 자체 레이아웃 프로그래밍 언어를 만들지 않는다.

다른 도메인에 편집기를 넣으면 브라우저 저장 영역도 달라질 수 있다. 기존 초안이 자동으로 공유된다고 약속하지 않는다. 동일 출처의 클라이언트·API 배치를 초기 기본으로 하고, 도메인 변경 시 파일 내보내기·가져오기 절차를 제공한다.

## 5. 문서 원본과 브라우저 저장

### 문서의 최소 계약

- `schemaVersion`: 문서 형식 버전.
- `documentId`, `revision`: 문서 정체성과 변경 충돌 확인.
- `title`, `content`: 제목과 제한된 노드·속성으로 구성된 본문.
- `media`: 이미지 ID, 원본 Blob 참조, MIME, 해상도, 표시 크기·정렬·설명, 파생본 참조.
- `exports`: 내보낸 문서 버전, 목적지, 생성한 결과물, 외부 게시 위치와 검증 상태.
- `updatedAt`, 문서 언어 등 필요한 메타데이터. UI 언어와 본문의 언어는 별개다.

Tiptap JSON을 기반으로 하되 허용한 노드·속성을 Wonboard 스키마로 문서화한다. 편집기 라이브러리 버전과 문서 형식 버전을 동일시하지 않는다. 알 수 없는 새 노드를 만났을 때 내용을 지우지 말고 원본을 보존한 읽기 전용 상태로 연다.

본문에는 이미지 식별자를 기록하고 실제 파일은 별도 Blob으로 저장한다. 원래 스크린샷 파일명은 메타데이터이며 키가 아니다. 외부 원본 파일을 지워도 로컬 사본이 남아야 한다. `blob:` URL은 미리보기용으로만 생성하고 저장 형식·게시 본문에 영구 기록하지 않는다.

### 자동저장과 복원

- 사진을 가져오면 Blob 저장과 문서 연결이 모두 성공한 뒤 '저장됨'으로 표시한다.
- 편집 중에는 메모리 상태와 디스크에 마지막으로 기록된 버전을 구분한다.
- 자동저장은 짧은 지연으로 묶되 마지막 저장 시점과 미저장 상태를 표시한다. `beforeunload`만으로 보존을 보장하지 않는다.
- 한글 조합 중 에디터를 다시 마운트하거나 본문을 재주입하지 않는다. 조합 완료 이벤트에서도 마지막 내용을 저장한다.
- 두 탭이 같은 문서를 열었을 때 버전 충돌을 감지하고 자동 덮어쓰지 않는다. 초기에는 두 번째 편집을 읽기 전용으로 제한해도 된다.
- 저장 공간 조회, 영구 저장 요청 결과, 용량 초과·권한 거부를 처리한다. 영구 저장 요청이 항상 허용된다고 가정하지 않는다.
- 로그인은 초안 동기화가 아니다. 첫 버전의 원본은 동일 브라우저·동일 출처에 있다.
- 로그아웃 시 로컬 문서를 자동 삭제하지 않는다. 동시에 서버 로그아웃을 로컬 파일 암호화로 설명하지 않는다. 공유 기기의 브라우저 프로필에는 초안이 남을 수 있음을 알린다.
- 문서와 원본 미디어 전체를 ZIP으로 내보내고 다른 브라우저에 복원할 수 있어야 한다. ZIP에 버전·파일 목록·검증값을 포함하고, 가져올 때 경로 이탈·누락·과도한 용량을 거부한다.
- 서비스 워커로 오프라인 실행을 추가할 때는 구버전 화면과 새 문서 스키마가 충돌하지 않도록 업데이트 안내와 마이그레이션 검증을 포함한다.

## 6. 사진과 공개용 저장

### 상태 전이

```text
로컬 원본 보관 → 편집·자동저장 → 게시용 버전 확정
  → 변환·업로드 → 공개 주소 확인 → 내보내기 준비 완료
                              ↘ 실패: 원본 보존·실패 항목만 재시도
```

로컬 자동저장과 공개용 업로드는 분리한다. 미리보기는 작성 중에도 로컬 파일로 즉시 제공하고, 업로드 완료 후에는 실제 공개 주소를 쓰는 결과 미리보기를 제공한다.

- 드래그는 우선 표시 폭과 정렬을 변경한다. 원본을 반복 축소해 덮어쓰지 않는다.
- 게시용 파일은 원본에서 생성한다. 고밀도 화면용 해상도와 본문 표시 폭을 분리하며 원본보다 확대하지 않는다.
- 캡처·투명 이미지는 PNG, 사진은 JPEG를 기본 추천한다. 실제 목적지의 제한에 따라 변환하고 투명도를 버릴 때는 결과를 미리 보여준다.
- 저장 이름은 충돌 없는 미디어·변환 버전 기반으로 생성한다. 원래 한글 파일명이나 문서 제목을 공개 주소에 자동 노출하지 않는다.
- 동일한 미디어와 변환 설정은 기존 파생본을 재사용한다. 이미지 정렬 순서는 파일명이나 업로드 완료 순서로 결정하지 않는다.
- 클라이언트에서 크기를 줄여 전송하되 서버에서도 실제 파일 형식·해상도·용량을 검사한다. 확장자나 클라이언트가 주장한 MIME만 믿지 않는다.
- 초기에는 정적 PNG/JPEG 사진을 필수로 한다. 애니메이션·SVG·HEIC 등은 지원 여부와 손실을 명시하고 조용히 다른 이미지로 바꾸지 않는다.
- 초기 기본 안전 상한 제안: 파일당 20 MiB, 디코딩 40 MP, 문서당 100장. 설정으로 조정하며 경계값 테스트를 작성한다.
- 공개 파일은 인증 없는 HTTPS 주소로 읽혀야 한다. 만료하는 업로드용 URL을 게시 본문에 넣지 않는다.
- URL 확인은 설정된 저장소·허용 출처에 한정한다. 임의 사용자 URL을 서버가 자유롭게 가져오는 기능은 만들지 않는다.
- 공개용 이미지 업로드는 외부 공개 행위다. 버튼·설정에서 그 의미를 분명하게 알린다. 비공개 원본과 공개 파생본은 별도 경로·정책을 사용한다.
- 외부로 복사한 이미지에는 '내보냄' 참조를 보수적으로 남긴다. 로컬 초안·서버 게시글 삭제만으로 해당 파일을 자동 제거하지 않는다.
- 공개 이미지의 주소·내용은 기존 게시물 기준으로 안정적으로 유지한다. 변경본은 새 주소를 사용한다. 공개 이미지 영구 삭제는 영향 안내와 별도 확인을 거친다.
- 1인 버전에서 개인 저장소 자격증명은 서버의 비공개 설정에 둔다. 프런트 번들·브라우저 저장소·공개 예제에 API 키를 넣지 않는다.

첫 클라우드 제공자는 지원의 결정에 따라 Google Drive다. 로컬 업로드 성공만으로 외부 게시판에서 사진이 보인다고 주장하지 않는다. 실제 Drive 저장과 외부 독자에게 이미지가 전달되는 경로를 각각 검증한다. 외부 호환성 테스트에 필요한 공개 권한은 별도로 확인한다.

## 7. 관리자 한 명을 위한 초기 인증

회원가입 제품은 뒤로 미루지만 인증 경계는 첫 서버 단계부터 구현한다.

- 로그인 이름은 `admin` 하나. 비밀번호는 지원이 비공개 설정 경로에서 정하며 대화·로그·GitHub에 기록하지 않는다.
- 서버에서 비밀번호 해시를 검증한다. 프런트의 문자열 비교나 `localStorage.isAdmin`으로 인증하지 않는다.
- 설정이 없으면 임의 기본 비밀번호로 열지 않고 안전하게 중지한다. 관리자 생성·재설정은 서버 운영 경로에만 둔다.
- 서버가 발급하고 만료·폐기할 수 있는 세션과 HttpOnly 쿠키를 사용한다. 공개 배포에서는 HTTPS와 Secure 쿠키가 필수다.
- 변경 요청에 CSRF 방어·Origin 검증, 로그인 시도 제한, 요청 크기 제한을 적용한다.
- 초안 API, 업로드 API, 게시판 설정, 비공개 파일 접근은 모두 서버에서 인증·권한을 검사한다.
- 기본 테스트 게시판은 비공개다. 공개 읽기와 공개 미디어는 명시적으로 켜는 독립 설정이다.
- 로그아웃·세션 만료 후 이전 세션으로 API 쓰기가 실패해야 한다. 로그인 만료가 로컬 원본을 지워서는 안 된다.
- 미래의 회원 기능을 위해 내부 작성자 ID를 남기되 현재 다중 사용자 화면을 만들지는 않는다.
- 초기 개발은 loopback에서 진행한다. NAS 설치, 포트 공개, 도메인·TLS·운영 비밀번호 설정은 별도 승인 이후 한다.

## 9. 게시판 엔진과 프리셋

초기 데이터는 `users`, `sessions`, `boards`, `posts`, `post_revisions`, `comments`, `media`, `media_references`, `publish_jobs`, `preset_overrides`를 중심으로 설계한다. 정확한 테이블은 M0에서 사용 사례와 함께 고정한다. 게시판마다 새 테이블을 만드는 방식은 채택하지 않는다.

- API → 인증·권한 → 입력 검증 → 도메인 처리 → DB·미디어 연결 → 응답 흐름을 공유한다.
- 글 수정은 예상 revision을 확인한다. 재시도하는 생성·게시 준비 요청은 같은 요청 키로 중복 생성을 막는다.
- 삭제는 먼저 휴지통 처리하며 글·댓글·사진마다 복원·공개 접근 정책을 구분한다.
- 댓글은 동일 게시물에 속한 부모만 허용한다. 초기 기본 최대 깊이는 3으로 두고 프리셋 설정으로 조정한다.
- 검색은 권한을 적용한 제목·본문 부분검색부터 제공한다. 한글 검색을 영어 어간 처리와 동일하게 취급하지 않는다. 작은 데이터 규모에서 시작하고 측정 후 전문 검색을 추가한다.
- 공개 글은 본문 HTML과 메타데이터를 서버에서 제공한다. 검색엔진이 앱 실행 후에만 본문을 볼 수 있는 구조를 기본으로 삼지 않는다.
- 확장은 타입이 있는 설정·테마 컴포넌트·명시된 이벤트로 시작한다. 관리자 화면에서 임의 코드를 실행하거나 외부 플러그인을 자동 설치하지 않는다.

첫 5개 프리셋 제안:

1. 한국식 목록: 공지·제목·작성자·날짜·댓글 수와 페이지 이동.
2. 이미지 갤러리: 같은 게시물을 썸네일 중심으로 표시.
3. 긴 글 중심: 본문 발췌·읽기 편한 글 화면.
4. 토론 피드: 투표·정렬·대댓글. 투표 중복과 권한을 서버에서 검사.
5. 질문·답변: 답변과 채택 상태. 채택 권한·삭제 시 상태 복구를 별도 검증.

목록 프리셋으로 공통 엔진을 완성한 뒤 차례로 추가한다. 첫 프리셋을 5개 완료로 보고하지 않는다. 추가 5개는 실제 사용 요구가 있을 때 정의한다. 투표·답변 채택 등 아직 없는 동작을 모양만 만들어 제공하지 않는다.

## 10. 한국어·영어의 완료 기준

- ko/en은 동등한 지원 언어다. 첫 방문은 브라우저 선호 언어로 정하고 명시 선택을 저장한다.
- 화면·메뉴·ARIA 이름·빈 상태·검증 오류·업로드 실패·관리 안내·기본 프리셋 이름에 번역 키를 사용한다.
- 서버는 안정된 오류 코드와 필드 정보를 반환한다. 클라이언트는 사용자 언어로 표시하며 기술 로그와 사용자 문구를 구분한다.
- UI 언어를 바꿔도 사용자 글을 번역하거나 수정하지 않는다.
- 한글 IME 조합 중 Enter·Backspace·방향키·붙여넣기·Undo/Redo·자동저장·사진 삽입을 검증한다.
- `Enter`는 문단, `Shift+Enter`는 문단 안 줄바꿈으로 정의하고 내보내기·재가져오기에서도 유지한다. 빈 문단과 연속 빈 줄을 조용히 제거하지 않는다.
- 한글 완성형·분해형 파일명, 한영 혼합 제목, 이모지와 결합 문자를 포함한다. 검색용 정규화와 원본 보존을 분리한다.
- 영문 대소문자와 한글 1~2글자 검색의 기대 동작을 사례로 고정한다. FTS 기본 설정이 모든 한글 요구를 해결한다고 가정하지 않는다.
- 날짜 저장은 UTC, 표시는 사용자 언어·시간대에 따른다. 문자열 정렬과 날짜 정렬을 혼동하지 않는다.
- 실제 한국어 입력 확인은 단순 문자열 주입 테스트와 구분한다. 자동화로 입증하지 못하면 지원의 실제 입력 확인 항목으로 남긴다.

## 11. 디자인 기준과 호환성 기준

### WordPress 원본 재현

지원이 선택한 WordPress Playground의 `/wp-admin/post-new.php` 편집 화면이 기준이다. 기존 CUA 확인에서는 제목·본문 캔버스, 상단 도구, 오른쪽 Post/Block 패널이 보였다. Playground 자체 하단 도구는 제품 화면이 아니다.

M0에서 WordPress 버전·테마·실제 폰트·스타일 수치·화면 크기·선택 상태를 기록하고 기준 이미지를 고정한다. 이전 스크린샷은 출발점이며 현재 버전 수치를 추정하지 않는다. 원본과 같은 조건에서 영문 기준 화면을 비교하고 한국어 화면도 따로 확인한다.

첫 작성 범위는 제목·문단·줄바꿈·강조·링크·목록·인용·사진·사진 설명·크기·정렬·실행 취소·재실행·문서 구조 탐색·서식 패널·저장·미리보기·내보내기다. 해당 범위의 화면과 조작 상태는 실제로 동작해야 한다. WordPress의 사이트 제작·상품·외부 플러그인 블록 전체 지원은 별도 범위다.

초기 필수 기능 목록에 없는 원본 컨트롤이 보이면 삭제·가짜 구현으로 얼버무리지 말고 M0의 화면별 목록에 처리 방식을 기록해 확인받는다. 특히 Wonboard의 공개 업로드와 WordPress의 Publish는 동작 의미가 다르므로 버튼 문구·상태 차이를 승인된 차이로 남긴다.

시각 검증은 동일 브라우저·viewport에서 원본과 구현을 나란히 확인한다. 글꼴·크기·굵기·행간·여백·패널 폭·아이콘·테두리·포커스·스크롤을 항목별로 기록한다. 확인하지 못한 폰트를 임의 값으로 정하고 완벽한 재현이라고 보고하지 않는다.

### 외부 게시판

- 목적지 프로필은 허용 태그·속성·스타일·이미지 방식·줄바꿈·본문 폭과 검증일을 가진다.
- 서식 있는 복사와 HTML 소스 복사를 구분한다. 필요하면 일반 텍스트도 제공한다.
- 붙여넣기 직후, 실제 게시 후, 새로고침 후를 구분해 검증한다.
- 준비된 본문은 테스트했지만 실제 게시하지 않았다면 '게시 검증 완료'라고 표시하지 않는다.
- 에디터별 차이를 먼저 찾고 사이트별 예외를 얹는다. 인기 사이트 10개 성공을 하나의 공통 규칙으로 추정하지 않는다.
- 첫 외부 목적지는 PGR21. 이후 사이트 목록·계정·테스트 게시판을 정해서 확장한다.
- 작은 비민감 테스트 문서만 사용한다. 사이트 규칙을 확인하며 가입·예상하지 못한 동의·CAPTCHA 등은 지원에게 넘긴다.
- 테스트 글의 생성 URL, 비교 증거, 삭제 결과를 기록한다. 계정 비밀번호·쿠키·개인 초안은 증거 자료에 포함하지 않는다.

### 수치가 있는 최소 검증 묶음

- ko/en 번역 키 불일치 0, 필수 화면에서 원시 번역 키 노출 0.
- 20개 문서 사례: 한영 혼합·빈 문단·긴 링크·목록·인용·이모지·한글 파일명·사진 설명·표시 크기 포함.
- 모든 사례에서 원본 → ZIP → 새 브라우저 복원 후 정규화 문서와 원본 미디어 검증값 일치.
- 20,000자·사진 50장 문서를 열고 편집·저장·복원. 테스트 기기와 지연을 기록하고 입력 차단·이미지 누락 0.
- 저장 실패·용량 초과·새로고침·네트워크 단절·중복 저장·부분 업로드 실패 각각 회귀 테스트 최소 1개.
- 미인증·만료 세션·잘못된 CSRF·다른 게시물의 미디어·다른 부모 댓글 등 권한·무결성 거부 테스트.
- 데스크톱 Chromium·Firefox·WebKit 자동화로 핵심 흐름 확인. WebKit 자동화를 실제 Safari 검증이라고 표현하지 않는다.
- 실제 Mac 한국어 IME 확인은 별도 증거. 모바일 폭에서는 읽기·기본 편집과 화면 넘침을 확인하되 모바일 전체 UX 완성을 주장하지 않는다.
- 최초 영어 기준 viewport와 한국어 동일 폭 비교. 일치 대상의 남은 레이아웃·폰트 차이는 0이어야 하며 승인된 차이만 예외 목록에 둔다.
- 빌드·타입 검사·단위 테스트·브라우저 테스트 명령을 루트 스크립트로 제공한다. 아직 존재하지 않는 명령의 성공을 보고하지 않는다.

## 13. 재사용·운영·에이전트 인터페이스

- 영어 README와 한국어 안내, 설정 JSON Schema, API 요청·응답·오류 예제, 최소 설치·진단·백업·복원 경로를 제공한다.
- 관리 기능은 API와 동일한 권한·검증을 이용한다. MCP 전용 우회 관리자 권한을 만들지 않는다.
- 초기 CLI는 설치 점검·설정 검증·백업·복원에 집중한다. 실제 설치된 환경의 상태를 확인하고 불완전 설정을 진단할 수 있어야 한다.
- 서버 생성·수정 요청은 예상 버전과 재시도 식별자를 사용한다. 문서·도구 설명의 힌트를 보안 집행으로 취급하지 않는다.
- 플러그인 설치·코드 실행·회원 공개 등록·파괴적 변경은 권한을 분리한다. 초기에는 임의 플러그인 자동 설치를 제공하지 않는다.
- 브라우저 백업, 서버 DB 백업, 공개 이미지 저장소 백업을 구분한다. DB 백업만으로 외부 사진까지 복원됐다고 보고하지 않는다.
- 업데이트는 사전 백업과 복원 절차를 함께 갖추고 사용자 프리셋 수정과 기존 문서를 대상으로 테스트한다.

## 14. 남은 사용자 결정과 외부 작업 경계

해결된 사용자 결정:

1. Wonboard 자체 코드의 MIT 라이선스 사용을 승인받았다. 실제 의존성·자산의 라이선스 검토는 별도 유지한다.

다음 착수 전 확인:

1. 이 문서의 추천 기술 구성과 단계별 범위를 구현 계획으로 승인할지 확인한다. 이미 확정한 웹·1인 관리자·ko/en·두 제품·MIT 결정을 다시 묻지 않는다.

외부 연동 단계에서 확인할 사항:

1. 실제 공개 이미지 저장소와 도메인·계정. 기존 리소스를 먼저 확인하고 유료 리소스 생성·공개 권한 변경은 사전 승인한다.
2. NAS 또는 다른 테스트 서버의 구체적인 위치와 접근 범위. 초기 로컬 검증에는 필요하지 않다.
3. Onsoon Labs 실제 홈페이지 작업 경로·브랜치·배포 승인. 이 저장소의 예제 호스트 검증과 구분한다.
4. 외부 커뮤니티별 테스트 가능한 계정·게시판·게시 및 삭제 범위.

중단 조건:

- 사용자 원본 손실 또는 기존 변경분 덮어쓰기 위험.
- 공개할 수 없는 라이선스·자산 조건 또는 목표 화면 재현의 핵심 가정 실패.
- 새 외부 유료 서비스, 배포, 원격 데이터 변경, 인증·공개 접근 확대가 필요하지만 승인이 없음.
- 사용자 결정이 없으면 문서·공개 범위가 달라지는 경우.
- 같은 원인으로 3회 연속 실패하고 안전한 대안으로 진행할 수 없음.

## 부록 A. 승인 후 사용할 실행 프롬프트

다음 프롬프트는 지원이 구현 범위를 승인하고 실행을 요청할 때 사용한다. 이 문서에 적혀 있다는 이유만으로 실행하지 않는다.

> 지원을 위한 Wonboard 웹 워드프로세서와 설치형 게시판을 구현한다. 지원은 실시간으로 보고 있지 않다. 목표는 사람이 직접 사진과 서식을 다듬어 글을 작성하고, 원본을 보존한 채 원하는 목적지에 게시하는 경험이다. 서버는 에이전트가 설치·변경하기 쉬워야 하지만 AI가 글을 대신 쓰는 경험을 제품의 중심으로 만들지 않는다.
>
> 먼저 이 계획의 확정 결정·미정 항목과 현재 저장소 상태를 확인한다. 라이선스 등 착수 전 결정이 해결됐는지 확인한다. M0의 기준 화면·문서 계약을 고정하고 M1부터 순서대로 진행한다. 승인된 범위의 로컬 파일 변경, 계획에 명시한 무료 오픈소스 개발 의존성 설치, 빌드·단위 테스트·브라우저 검증은 질문 없이 수행한다. 버전은 실제 설치 시 확인하고 고정한다. 기존 사용자 변경은 보존한다.
>
> 원격 push·PR·merge·배포·운영 DB 마이그레이션·계정 생성·유료 리소스·공개 권한 확대는 이 프롬프트의 승인에 포함되지 않는다. 공개 저장소 생성 승인을 이후 main push 권한으로 확대하지 않는다. 외부 게시 테스트는 별도 승인 범위에 한해서 수행하며 사이트별 확인이 없으면 멈춘다.
>
> 구현하는 UI는 지원이 지정한 WordPress 실제 화면을 기준으로 비교한다. 신규 생성 시안이나 다른 제품 화면으로 대체하지 않는다. 한국어·영어, 한글 실제 입력, 사진 크기·순서, 저장·복원, 업로드 실패, 권한 검증을 단계별로 확인한다. 위 수치 게이트를 통과하지 않은 단계는 완료로 보고하지 않는다.
>
> docs/planning/progress.md에 마지막 완료 단계, 변경 파일, 실행한 명령과 결과, 미검증 항목, 다음 시작 지점을 기록한다. 끊겼을 때는 그 기록과 실제 git 상태·실행 상태를 재확인해서 이어간다. 문서에 완료라고 적혀 있어도 현재 산출물 증거와 다르면 재검증한다. 중단 조건에서는 위험과 필요한 결정을 알리고 멈춘다.
