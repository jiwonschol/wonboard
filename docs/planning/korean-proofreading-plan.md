# 한국어·영어 통합 맞춤법 검사: 수정안 생성까지 구현하는 실행 지시서

작성일: 2026-09-09. 개정: 2026-09-09 (어휘 데이터 정책 확정, 베이스라인 고정, 게이트 계측). **계획 및 이슈 등록 단계. 이 문서의 작성은 구현·새 의존성·PR·배포 승인이 아니다.** 지원의 후속 실행 승인 이후 아래 범위로 진행한다. 완료는 일반적인 한국어 전체를 해결했다는 뜻이 아니라 아래 공개된 범위와 시험을 통과했다는 뜻이다.

## 1. 누구를 위한 무엇인가

Wonboard는 사람이 공들여 쓴 글을 커뮤니티로 내보내는 워드프로세서다. 작성자의 문체, 게임 용어, 게시판 약칭을 보존하면서 철자와 띄어쓰기 수정안을 제안한다. AI의 문장 재작성, 문체 순화, 문단 나누기 프리셋은 이 작업에 포함하지 않는다. 사용자가 API 키를 입력할 필요가 없어야 하며 초안을 외부 서비스에 전송하지 않는다.

지원이 겪은 실패는 검사창의 모양이 아니라 수정안 부재다. ‘사전에 없음’을 발견하고 ‘확인해 보세요’만 보여주는 것은 띄어쓰기 검사가 아니다. 수동 입력창만 제공하는 것도 수정안 생성의 대체물이 아니다.

### 언어별 범위와 공통 경험

하나의 ‘맞춤법 검사 / Check spelling’에서 한국어와 영어를 함께 검사한다. 표시 언어(ko/en UI)와 검사 대상 언어는 독립적이다. 언어별 창을 열게 하지 않고 한영 결과를 원문 순서대로 검토한다.

| 언어 | 이번 구현 | 후속 범위 |
| --- | --- | --- |
| 한국어 | 철자, 띄어쓰기, 미등록 표현, 사용자 사전과 조사 처리 | 일반 문맥·문장 문법 전체 |
| 영어 | 철자 오류의 실제 수정안, 미등록 표현, 사용자 사전 | 수일치·시제·관사 등 문법 검사 |
| 한영 혼용 | 언어 구간과 조사 경계, 원문 순서의 통합 검토 | 문장 재작성·번역 |

전통적인 Word의 ‘검사 → 변경 또는 무시 → 다음 항목’을 참고한다. 점수·문체 개선·자동 교정은 포함하지 않는다. 화면 통합을 엔진 기능의 동등성으로 설명하지 않는다. 영어 문법을 검사하지 않았는데 문법까지 통과했다고 표시하지 않는다. 참고: [Microsoft Word 검사 안내](https://support.microsoft.com/en-us/word/training/check-grammar-spelling-and-more-in-word).

## 2. 착수 지점 — 어디서 작업하는지가 먼저다

**본체 체크아웃 `/Users/jiwon/develop/projects/wonboard`의 브랜치 `codex/desktop-local-storage`에서 작업한다.** 아래 상태의 일부는 커밋되지 않고 그 작업 디렉터리에만 있다. git worktree는 커밋된 내용만 새로 체크아웃하므로, 새 워크트리나 새 클론에서 시작하면 그 부분이 통째로 사라지고 이미 만들어진 UI를 처음부터 다시 만들게 된다. 워크트리를 새로 만들지 않는다(§9 금지선).

`main`에는 맞춤법 코드가 존재하지 않고, `codex/korean-spelling-review`에는 Electron 클라이언트가 없다. 커밋된 베이스는 `1deaddf1d51125ec22d04ba0f43eb640cc1824af`("Add shared Electron desktop client with local SQLite storage")다.

착수 시 `git rev-parse HEAD`, `git status --short`, `git log --oneline -5`를 실행해 출력을 검증 기록에 남긴다. **`git status --short`에 아래 ‘커밋되지 않은 상태’ 목록이 보이지 않으면 잘못된 위치에서 시작한 것이다. 멈추고 보고한다.**

### 커밋된 상태

- `packages/editor/src/spelling.ts`: 연속 한글(`/[가-힣]+/`)을 한 덩어리로 추출하고, 서식으로 쪼개진 조각을 완성된 단어로 오인하지 않도록 앞뒤 문자를 확인한다. `codeBlock`과 `code`·`link` 마크는 제외한다. 사용자 사전은 localStorage의 `wonboard.spelling.personal.v1` 문자열 배열이며 정확히 일치하는 표현만 제외한다.
- `packages/editor/src/spelling.worker.ts`: Hunspell `spell`과 `suggest`를 호출한다. 메시지 프로토콜은 `string[]`을 받아 `{word, suggestions}`를 돌려주는 단어 단위이며, 문장 단위 분절 엔진은 없다.
- `packages/editor/src/SpellcheckTool.tsx`: **추천 버튼을 누르면 즉시 본문을 교체한다.** 문서 snapshot과 누적 offset으로 교체 위치를 관리하고, 건너뛰기·이번 검사 무시·사용자 사전·`closeHistory` 기반 undo 연계가 있다.
- `apps/desktop/src/renderer.tsx`: 웹 App을 공유한다. 웹·데스크톱별 검사 엔진을 따로 만들지 않는다.
- `public/spelling/NOTICE.md`: 엔진·wrapper·사전의 조건은 서로 다르며 현재 전체 의존성이 MIT인 것은 아니다. 사전 GPL이 앱 전체를 자동으로 GPL로 바꾼다고 단정하지 않는다.
- `tests/e2e/spelling.spec.ts`: 적용·건너뛰기·사전 지속·되돌리기 흐름을 검사한다. 한국어 일반 정확도를 증명하지 않는다.

### 커밋되지 않은 상태 — 이것도 베이스라인이다

다음은 작업 디렉터리에만 있고 어느 브랜치에도 없다. **커밋되지 않은 것이 정상이다. 커밋을 기다리지 말고 이 상태 위에서 이어서 작업한다.** 다만 되돌릴 지점이 없으므로, 이 파일들을 크게 재작성하기 전에 작업 브랜치에 먼저 커밋해 복구 지점을 만든다(§9에서 로컬 커밋은 사전 승인됨).

- `SpellcheckTool.tsx`·`spelling.css`·`style.css`·`locales/src/index.ts`·`tests/e2e/spelling.spec.ts`의 수정분: 추천은 선택만 하고 ‘바꾸기’로 적용하는 UI와 직접 입력 필드를 추가한다. §6의 확정 UX 중 이 부분은 이 diff가 살아 있어야 이미 만족된 상태다.
- `docs/planning/korean-proofreading-plan.md`(본 문서)와 `docs/spelling-engine-evaluation.md`.
- 미완성 `WhitespaceTool.tsx`·`whitespace.ts`와 그 테스트 2개. 현재 후행 공백 제거와 빈 문단 정리만 하며 한국어 어절 경계를 추론하지 않는다. **이 트랙은 이번 범위가 아니다. 되돌리지도, 함께 손대지도, 배포하지도 않는다.**

`docs/spelling-engine-evaluation.md`는 이전 후보 조사다. 가중치·데이터 조건을 확인하지 않은 후보를 승인된 의존성으로 취급하지 않는다. 기존 초안과 사용자 사전, 사진, Sites 인증·D1/R2는 보존한다.

## 3. 기능 계약과 기준 사례

사용자 제공 문장:

> 평소에 질게에서답변하시는걸 뵌걸로보면 제가 조언할 수준은 아닌것 같지만

첫 필수 결과는 `질게에서답변하시는걸`에 `질게에서 답변하시는 걸`을 제안하는 것이다. `질게`는 ‘사전에 없는 표현’으로 별도 검토할 수 있어야 한다. 이 단어를 ‘질문 게시판’ 등으로 자동 치환하지 않는다. 이 문장 전체의 유일한 정답을 임의로 고정하지 말고 나머지 표현은 규정과 문맥을 확인해 독립 사례로 만든다.

1. 등록 전에도 알 수 없는 명사 때문에 주변 띄어쓰기 후보 생성 전체가 실패하지 않아야 한다.
2. 띄어쓰기를 적용한 뒤에도 필요한 경우 `질게`의 사전 등록을 안내한다. 겹치는 두 수정안을 오래된 위치에 연달아 적용하지 않는다.
3. `질게` 등록 후 `질게에`, `질게에서`, `질게는`을 인식한다. 등록된 문자열을 포함한다는 이유만으로 임의의 긴 단어를 모두 허용하지 않는다. 사전 삭제 후 동일 문장을 재검사하면 원래 동작으로 돌아온다.
4. 사전에 등록해도 그 단어 주변의 띄어쓰기 검사는 계속한다. 문장 전체를 검사 제외하지 않는다.
5. 추천 선택은 미리보기이며 ‘바꾸기’가 실제 변경이다. 한 번의 적용은 한 번의 undo로 돌아간다. 건너뛰기는 내용을 변경하지 않는다.
6. 후보가 없으면 ‘제안을 만들지 못함’으로 표시한다. 모든 제안이 끝난 것과 문장이 올바르다는 판정을 구분한다.

### 영어·혼용 기준 사례

- `I will recieve the item.`에서 `recieve → receive`를 제안한다. 이 사례만 고정한 치환표로 영어 검사 완료를 선언하지 않는다.
- `WoW에서 recieve한 아이템`에서 `WoW에서 receive한 아이템`으로 해당 부분만 바꾼다. `WoW`의 대소문자와 한글 조사·어미를 보존하고 문장을 다듬지 않는다.
- 정상 영어, 축약형(`don't`), 소유격, 하이픈, 약어, 숫자 혼용 식별자, URL·코드 제외를 별도 시험한다. 단어 내부 apostrophe를 무조건 분리하지 않는다.
- 미국식·영국식으로 모두 인정되는 표기는 서로 교정하도록 강제하지 않는 것을 초기 기본값으로 둔다. 자료가 한 변종만 다룬다면 지원 범위를 밝힌다.
- 사용자 사전은 한영 표현을 모두 저장한다. 영어는 등록한 대소문자를 보존하며 무조건 소문자화하지 않는다. 영어 등록어에 한국어 조사가 붙어도 인식한다. 기존 한국어 항목을 삭제하거나 전부 영어로 재분류하지 않는다.

## 4. 구현 방향 — 코드는 자체 MIT, 어휘 데이터는 허용 라이선스 채택

**확정 정책(2026-09-09 지원 결정): 검사 로직은 처음부터 직접 작성한 MIT 코드로 만들고, 어휘·품사 데이터는 Apache 2.0 등 표기 의무만 있는 라이선스의 기존 자료를 채택한다.** 어휘를 손으로 쓰는 방식은 폐기한다.

이 결정의 이유를 실행자가 알아야 한다. 한국어 띄어쓰기 후보 생성은 규칙만으로 성립하지 않는다. `질게에서답변하시는걸`을 쪼개려면 ‘답변’이 명사이고 ‘하시는’이 활용이며 ‘걸’이 의존명사라는 어휘 지식이 필요하다. 걷어내려는 hunspell-dict-ko는 10만 항목 규모이고, 그보다 나은 동작(철자뿐 아니라 띄어쓰기 제안)을 손으로 쓴 소규모 어휘로 달성한다는 전제는 §8의 수치와 양립하지 않는다. 지원의 제약은 “데이터를 직접 만들 것”이 아니라 **“GPL 이상의 전염성 라이선스를 피할 것”**이므로, 표기 의무만 있는 자료는 제약을 위반하지 않는다.

### 채택 후보와 채택 조건

아래는 조사 시점에 라이선스를 확인한 후보다. **실행자는 여기 적힌 라이선스를 사실로 전제하지 말고, 원문 LICENSE·NOTICE 파일을 실제로 내려받아 저장소에 커밋한 뒤에만 사용한다.** 원문을 확보하지 못한 자료는 채택하지 않는다.

| 자료 | 조사 시점 라이선스 | 용도 |
| --- | --- | --- |
| [mecab-ko-dic](https://github.com/LuminosoInsight/mecab-ko-dic) | Apache 2.0 | 한국어 명사·조사·어미·품사. Apache Lucene의 Nori 분석기가 이 사전 기반으로 ASF에 들어갔다 |
| [open-korean-text](https://github.com/open-korean-text/open-korean-text) | Apache 2.0 | 명사/조사/어미 목록이 텍스트 파일이라 크기가 작다. mecab-ko-dic 대신 또는 함께 |
| [SCOWL / hunspell en_US](https://wordlist.aspell.net/scowl_v1-readme/) | MIT 유사(저작권 고지 유지) | 영어 어휘 |

채택 시 지켜야 할 조건:

- **데이터만 가져오고 코드는 가져오지 않는다.** MeCab 엔진, 형태소 분석 라이브러리, 다른 검사기를 런타임 의존성으로 추가하지 않는다. 사전 데이터를 추출·가공해 자체 MIT 코드가 읽는 형식으로 만든다. 가공 스크립트도 저장소에 남긴다.
- **버전을 고정하고 출처를 기록한다.** URL, 태그/커밋, 취득 날짜, 원본 파일 크기, 추출 후 크기를 검증 기록과 NOTICE에 남긴다.
- **Apache 2.0의 의무를 이행한다.** LICENSE 사본, NOTICE 파일 보존, 가공했다면 변경 사실 고지. `public/spelling/NOTICE.md`와 `public/THIRD_PARTY_NOTICES.txt`를 새 구성물에 맞춰 갱신한다.
- **크기 예산.** 현재 `ko.aff`+`ko.dic`은 원본 13.6MB, gzip 약 830KB다. 새 어휘 자산은 **gzip 1.0MB 이하를 목표**로 하고, **2.0MB를 넘으면 진행하지 말고 멈추고 보고한다.** 전체 사전을 그대로 번들하지 말고 필요한 품사·필드만 추출한다.
- **여전히 채택하지 않는 것:** GPL 자료(hunspell-dict-ko, PyKoSpacing, soynlp), LGPL 라이브러리(Kiwi), 라이선스를 확인하지 못한 모델 가중치, 재배포 조건이 불명확한 학습 말뭉치. 유료 자원과 외부 API도 범위 밖이다.

### 제거 대상과 그 경계

대체 구현이 게이트를 통과한 뒤 hunspell-asm, 검사 전용 패치, 사용처가 사라진 전용 로더, `ko.aff`/`ko.dic`, 더 이상 배포하지 않는 엔진 자산을 제거한다. 제거 전 `grep -rn "hunspell\|spelling\|ko\.dic" --include='*.ts' --include='*.tsx' --include='*.json' . | grep -v node_modules`를 실행해 출력 전문을 기록하고, 나타난 사용처를 하나씩 판정한다. 다른 기능이 쓰는 구성물은 제거하지 않는다.

**git 히스토리를 재작성하지 않는다.** 제거는 작업 트리와 새 빌드 산출물에 대한 것이다. GPL 사전이 과거 커밋에 남아 있는 것은 고지 파일이 함께 있는 한 문제가 아니며, 오히려 과거 배포물의 고지 보존 의무에 부합한다. `filter-branch`, `filter-repo`, force push는 금지선이다.

GPL 사전 내용을 복사·변환해 자체 자료로 재명명하거나 기존 검사기를 숨은 fallback으로 남기지 않는다. 과거 배포물에 적용되는 고지와 의무는 새 버전에서 제거한다고 소급 소멸하지 않는다. 새 구현이 품질 기준에 못 미치면 실패 유형을 보고하며, 승인 없이 기존 엔진으로 회귀하지 않는다.

### 규칙의 근거

- [국립국어원 어문 규범](https://korean.go.kr/kornorms/m/m_regltn.do)을 띄어쓰기·철자 규칙의 근거로 삼는다. 규칙마다 조항 번호와 규정 원문 한 줄 인용, 직접 작성한 예문을 남긴다. **기억으로 조항 번호를 적지 않는다.** 원문을 확인할 수 없으면 그 규칙을 ‘근거 미확인’으로 표시하고 게이트 분모에서 빼지 않는다.
- 공식 규칙 자체와 그 사이트의 해설·사전 데이터에 대한 권리는 구분한다. 해설문을 복사하지 않는다.
- 상용 검사기 구매, API/SDK 연동은 제품 범위 밖이다. 특정 외부 검사기의 접근 가능 여부를 개발의 전제조건으로 삼지 않는다.
- 문맥에 따라 여러 해석이 가능한 사례는 허용 후보와 판단 근거를 기록한다.
- 검사 엔진이나 모델을 새로 학습하는 것은 범위 밖이다. 사용자 초안은 외부로 전송하지 않는다.

## 5. 텍스트·편집기 안전성

최소 검사 결과는 원문 범위, 원문 문자열, 언어(ko/en/혼용), 유형(철자/띄어쓰기/미등록어), 후보들, 간단한 근거, 적용 가능 여부를 가진다.

**현재 Worker 메시지 프로토콜은 이 결과를 담지 못한다.** `string[]` → `{word, suggestions}` 구조를 위 필드를 담는 구조로 교체한다. ‘기존 것을 재사용한다’는 말은 **Worker 수명주기(다이얼로그마다 하나, 닫으면 terminate)와 다이얼로그 셸·상태 구분을 유지한다**는 뜻이지, 낡은 프로토콜에 끼워 맞추라는 뜻이 아니다. 동시에 범용 플러그인 프레임워크나 검사 결과 캐시 계층을 새로 만들지도 않는다. 언어별 결과는 원문 위치로 합치고 같은 범위의 중복 제안과 상충 후보를 정리한다.

문단 텍스트와 ProseMirror 위치 매핑을 명시한다. 굵게/기울임 등으로 텍스트 노드가 나뉘어도 검사 가능해야 한다. 이미지·링크 대상·코드·문단 경계를 건너뛰어 붙이지 않는다. 코드와 URL은 수정하지 않으며 링크 텍스트 제외 정책은 기존 동작을 유지한다. NBSP, 일반 공백, 줄바꿈, 이모지의 UTF-16 길이를 구분한다. 검사 과정에서 원문을 정규화해 위치가 어긋나지 않도록 한다.

삽입 공백의 서식 소유 규칙을 정하고, 나머지 문자 서식·링크·사진·문단 구조는 보존한다. 문서 변경/한글 IME 조합/문서 전환으로 결과가 오래되면 적용을 막고 재검사한다. 적용 후 영향 문단의 겹치는 결과를 무효화하거나 재검사한다. 기존 사용자 사전은 읽을 수 있어야 하며 무단 초기화하지 않는다. 계정 동기화·DB 변경은 하지 않는다.

## 6. UI/UX 계약

기존 상단바·인스펙터 진입점을 유지하고 같은 검사 화면을 연다. 한국어/영어 UI 모두에서 두 언어를 함께 검사한다. 검사창은 원문 문맥, 강조된 범위, 오류 종류, 추천 수정안, 명확한 바꾸기를 제공한다. 낯선 단어는 오류 확정과 다른 표현을 쓴다. 영어 문법 같은 미지원 항목을 작동하는 분류로 표시하지 않는다.

첫 후보를 미리 선택할 수 있지만 자동 적용하지 않는다. 직접 입력은 보조 기능이다. 건너뛰기와 사용자 사전 추가는 기본 경로로 유지한다. 로딩/실패/후보 없음/완료/문서 변경 상태를 구분한다. 키보드, Escape, 포커스 복원, 화면 읽기 이름을 확인한다. 과도한 설명, 전체 UI 재설계, 강제 일괄 변경은 범위 밖이다.

### 확정 UX: 검사하되 고치도록 압박하지 않는다

- 규정 위반을 검출하면 표시한다. 덜 까다로운 UX를 만든다는 이유로 탐지를 숨기거나 무조건 정상으로 처리하지 않는다. 단, 미등록 표현이나 문맥상 애매함을 확정 오류로 표시하지 않는다.
- 기본 행동과 시각적 우선순위는 **그대로 두고 다음으로**다. 닫기/건너뛰기에 확인 팝업을 추가하지 않는다. 수정 여부로 완료 점수나 경고를 주지 않는다.
- 수정안은 읽기 쉽게 항상 보이되 적용은 명시적인 **바꾸기**로만 한다. 검사창 진입·다음 항목 이동 후 기본 포커스는 건너뛰기에 둔다. Enter가 암묵적으로 교정을 실행하지 않아야 한다. 바꾸기에 직접 포커스한 경우 Enter/Space로 실행할 수 있다. 입력창과 IME 조합 중 Enter는 의도하지 않은 적용·이동을 만들지 않는다.
- 모호한 경우 가능한 후보와 근거를 보여줄 수 있지만 ‘검토할 표현’으로 구분한다. 판단 불가능한 원문에 억지 정답을 만들지 않는다. 후보 미리보기는 원문/수정 후 표현을 함께 보여준다.
- 건너뛰기는 현재 발생 위치만, 이번 검사 무시는 해당 표현의 현재 실행 전체, 사용자 사전은 지속 적용이다. 재검사 때 내용·위치가 보존된 건너뛴 항목은 반복 강요하지 않는다. 새 문서나 새 검사 실행에 임시 무시를 영구 적용하지 않는다.
- 사전 등록 대상은 `질게`처럼 기본 표현을 미리 보여주고 수정 가능하게 한다. 최초 범위는 명사·약칭과 명시한 조사 조합이며 임의의 동사 활용 전체를 지원한다고 표시하지 않는다. 등록 후에도 주변 띄어쓰기 검사는 유지한다.

## 7. 단계와 산출물

### A. 판정 자료와 채점기를 먼저 만든다

기준 문장의 기존 Worker 결과와 추천 부재를 재현한다.

**한국어 120개**를 직접 작성한다: 철자 오류 25, 띄어쓰기 오류 35, 정상 문장 30, 고유명사/약칭/구어체/한영혼용 30. **영어 60개**(철자 오류 30, 정상 표현 15, 고유명사·축약형·변종 15)와 **한영 혼용 20개**를 더해 총 200개로 관리한다. 각 사례에 예상 범위와 허용 후보 집합, 규정 근거 또는 모호성 표시를 기록한다.

평가용 분리는 **유형별 비례**로 한다. 한국어는 철자 8·띄어쓰기 12·정상 10·혼용 10을 빼고(총 40), 영어 20개와 혼용 10개를 같은 방식으로 뺀다. 균등 10개씩 빼면 철자 개발 자료가 15개만 남아 게이트 수치의 근거가 되지 못한다. 동일 어근이나 문장 틀만 바꾼 자료는 사례군 단위로 같은 쪽에 배치한다. 기준 문장과 그 변형은 공개 회귀 시험으로 따로 둔다.

**`scripts/eval-spelling.mjs`를 A단계 산출물로 만든다.** 자료 JSON을 입력받아 §8의 분자/분모를 표로 출력한다. A단계 종료 시점에 엔진이 비어 있어도(전 항목 0점) 스크립트는 돌아가야 한다. 이후 모든 수치 보고는 이 스크립트의 표준출력을 그대로 붙여넣는 것으로만 한다.

지원이 본인이 쓴 커뮤니티 글에서 20~40문장을 홀드아웃으로 제공하면 그것을 최종 평가 세트로 삼는다. 제공 전이라면 자체 세트로 진행하되, **같은 실행자가 시험지와 규칙을 모두 작성했으므로 이 수치는 독립 평가가 아니라는 사실**을 보고에 명시한다. 평가 실패 후 규칙을 수정했다면 그 세트가 더 이상 미사용 평가 세트가 아님을 기록한다. 정답의 최소 편집 위치·허용 최종 문자열·모호성 여부는 결과를 보기 전에 고정한다.

### B. 로컬 엔진 프로토타입

채택한 어휘 데이터를 추출·가공하고, 미등록 명사와 조사 처리, 띄어쓰기 후보 생성, 철자 추천을 연결한다. 원인 분리를 위해 띄어쓰기 단계는 비공백 문자를 유지하고 공백 삽입·삭제만 제안하며, 철자 변경은 별도 유형으로 검증한다. 기준 문장의 고유 문자열을 하드코딩하지 않는다. 등록 전/후/삭제 후와 다른 약칭으로 일반화 여부를 확인한다.

영어 토큰 추출·철자 후보와 한국어 조사 경계를 독립 검증한 뒤 결과를 통합한다. 표시 언어를 바꿔도 검사 결과가 바뀌지 않아야 한다. 한 언어 검사 실패로 다른 언어까지 정상 판정하지 말고 실패 범위를 명시한다.

**B단계 조기 게이트 — 여기서 걸러야 한다.** 기준 문장과 평가용 세트로 `scripts/eval-spelling.mjs`를 돌린다. 한국어 탐지 재현율 70% 미만이거나 정상 문장 오탐이 3건을 넘으면 **C단계로 넘어가지 않는다.** 수치, 실패 문장, 원인 분류, 선택지 하나를 남기고 멈춘다. UI 통합을 끝낸 뒤에 처음 수치를 보는 일이 없어야 한다.

### C. 공유 편집기 통합

범위 매핑·서식 보존·충돌 무효화·undo를 구현하고 UI에 유형과 실제 추천을 연결한다. 웹과 Electron에서 동일 코드를 사용한다. 사용자 초안을 시험 데이터로 덮어쓰지 않고 별도 로컬 시험 문서를 사용한다.

### D. 검증 및 인계

§8 기준의 분자/분모, 실패 문장, 시험 환경, 코드 revision을 문서로 남긴다. 제한된 평가 결과를 한국어 전체 정확도로 홍보하지 않는다. 로컬 검증 결과와 배포/설치 여부를 분리해 보고한다. 이슈를 구현 전에 닫지 않는다.

## 8. 완료 게이트 — 모두 통과해야 구현 완료

다음 수치는 초기 목표이며 실제 측정 결과가 아니다. 실패하면 수치를 낮춰 통과 처리하지 말고 지원에게 범위/비용 판단을 요청한다. **모든 수치는 `scripts/eval-spelling.mjs`의 출력으로 보고한다. 서술형 자기보고는 인정하지 않는다.**

### 정확도

- [ ] 기준 사례 및 등록 전/후/삭제 후, 다른 약칭 변형 10개 모두 기대 동작 통과.
- [ ] 한국어 자료에서 철자·띄어쓰기 각각 오류 범위 탐지 재현율 90% 이상. 후보 없는 탐지도 분모에 포함한다.
- [ ] 올바른 수정안이 상위 3개 안에 포함된 오류 비율 85% 이상. **이 항목은 위 재현율과 독립으로 보고하며, 한쪽을 올리려고 다른 쪽 임계값을 조정했다면 그 사실을 기록한다.**
- [ ] 정상 문장 30개에서 잘못된 변경 추천 0건. 미등록어 확인 안내와 잘못된 변경 추천을 별도 집계한다. **이 0건은 정상 문장 세트에만 적용되며, 이 수치를 맞추려 탐지 임계값을 올려 재현율을 희생했다면 두 수치의 변화를 함께 보고한다.**
- [ ] 혼용/약칭 30개에서 보존 대상으로 정한 문체·고유명사의 잘못된 교체 추천 0건. 자동 적용 0건은 별도 UI 안전성 시험이다. 미등록어 안내 건수도 별도 보고한다.
- [ ] 오류 이벤트별 탐지율, 첫 후보 정확도, 상위 3개 후보 정확도, 문장 전체 정확 일치를 분리 보고한다. 공백 누락은 문자 사이 경계 이벤트로 정의하고 동일 오류 중복은 하나로 센다. 범위가 달라도 허용 최종 문자열을 만들고 불필요한 추가 변경이 없으면 정답으로 인정한다. 후보 없음과 탐지 누락도 전체 오류 분모에 포함한다.
- [ ] 이 수치를 전체/분리 평가용 세트 각각 보고. 좁은 데이터와 자기 작성 시험지의 일반화 한계를 명시.
- [ ] 구현 후 새 어휘·문장 구조 20개(한국어·영어·혼용 포함)를 추가 점검. 여기서 실패해 수정했다면 재사용 사실을 남긴다.
- [ ] 영어 오류 30개에서 탐지율 90% 이상, 정답 상위 3개 포함 85% 이상을 별도 달성. 첫 후보 정확도·미등록어 안내 건수와 실패를 별도 보고. 한 언어 점수로 다른 언어 실패를 상쇄하지 않는다.
- [ ] 정상 영어·보존 대상 고유명사/축약형/변종에서 잘못된 교체 추천 0건. 혼용 20개에서 문자·조사·대소문자 보존 및 원문 순서 통합을 검증.

### 동작과 안전성

- [ ] 띄어쓰기·철자 각각 실제 클릭 적용, 건너뛰기, 사전 등록/해제, undo/redo, 문서 전환, 검사 중 변경, IME 조합을 검증.

## 10. 실행 계측 — "확인한다"는 전부 도구 실행을 뜻한다

**기억이나 추론으로 조회를 대체하지 않는다.** 아래 각 항목은 실행한 명령과 그 출력을 검증 기록에 그대로 남긴다. 출력을 남기지 못한 항목은 미확인으로 보고하고, 확인한 것처럼 서술하지 않는다.

- **착수:** `git rev-parse HEAD` · `git status --short` · `git log --oneline -5`. §2의 작업 위치 조건을 만족하지 않으면 멈춘다.
- **라이선스 판정:** “MIT다/Apache다”라고 서술하지 않는다. 원문 LICENSE·NOTICE 파일을 내려받아 저장소에 커밋하고 취득 URL·버전·크기·취득일을 함께 기록한다. 원문을 확보하지 못한 자료는 채택하지 않는다.
- **어문 규범 근거:** 규칙마다 조항 번호와 규정 원문 한 줄 인용을 남긴다. 기억으로 조항 번호를 적지 않는다.
- **기존 자산 제거 전:** §4의 `grep` 명령을 실행하고 출력 전문을 남긴다. 출력에 나타난 사용처를 판정하기 전에는 어떤 파일도 지우지 않는다.
- **게이트 수치:** `node scripts/eval-spelling.mjs`의 표준출력 전문을 붙여넣는다. 스크립트가 없으면 A단계가 끝나지 않은 것이다.
- **크기 측정:** 빌드 산출물의 실제 gzip 크기를 명령으로 측정해 기록한다. 추정치를 쓰지 않는다.
- **단계 종료마다** `docs/planning/spelling-progress.md`에 실행한 명령, 산출물 경로, 수치, 미확인 항목을 append한다. 덮어쓰지 않는다.

보고하는 주장은 이 세션의 실제 도구 결과에 대응해야 한다. 검증하지 못한 것은 검증하지 못했다고 말한다.
