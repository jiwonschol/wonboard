## 목표와 권한

작성 중 파일을 찾아 원래 커서에 넣고, 독립 보관·공유와 고정 글 스냅샷을 관리한다. 다중 문서·공개 주소·스냅샷이 필요한 바이트는 삭제하지 않는다. 아래 게이트를 함께 통과해야 2단계 완료다. 보관함 화면만 완성한 것으로 끝내지 않는다.

정본: [#9 본문과 코멘트](https://github.com/jiwonschol/wonboard/issues/9), [#8](https://github.com/jiwonschol/wonboard/issues/8), [#10](https://github.com/jiwonschol/wonboard/issues/10), [#11](https://github.com/jiwonschol/wonboard/issues/11). 최신 지원 결정 `f44ed9d31694e26a509c57e6408baa3300c48c733cff9416405b568cfa43bc2a`와 동준의 실행 지시 `512975dc724dd967cf8cf4446e9555535a1bb14b4dd674dc22ebda4c8353ec8b`가 옛 결정과 아래 초기 조사 기록보다 우선한다. #14의 휴지통·복구 캐시와 #15 설치 안내는 재구현하지 않되, 글 삭제 화면의 게시 사진 체크박스는 2단계에서 제거하고 보관함의 별도 철회/삭제로 옮긴다.

이번 산출물은 실행 계획이다. 새 제품 선택은 동준이 지원에게 묶어 전달한다. 2026-09-16 후속 지시에 따라 로컬 구현·마이그레이션 파일 작성 자체는 이슈 처리 요청에 이미 포함되므로 재승인을 요구하지 않는다. 제품 선택에 의존하는 부분은 답을 반영해 이어간다. 운영 업로드·삭제·배포·DB 마이그레이션, merge와 main push는 제외한다. 문서 PR도 신원 확인을 선행한다.

## 저장 모델 제안

사진 원본과 범용 파일을 무리하게 같은 테이블로 옮기지 않는다. 기존 media/publications 및 URL을 유지하고 참조 장부를 덧붙인다. 아래 이름은 구현 시 조정 가능한 설계 이름이다.

| 객체 | 핵심 필드·관계 | 보존 조건 |
| --- | --- | --- |
| 파일 `files` | 불변 id/object_id, 원래 이름·표시 이름, MIME, 크기, SHA-256, revision, trashedAt | 독립 보관 자체가 참조. 글에서 제거했다고 삭제하지 않음 |
| 바이트 `objects` | 불변 key/hash/size, 상태 uploading/ready/deleting/deleted, 세대, 업로드 예약 | 유효 참조 또는 진행 중 작업 예약이 있으면 보존 |
| 문서 참조 `document_file_refs` | document_id + file_id, 문서 revision과 같은 트랜잭션에서 교체 | 활성 문서 및 복원 가능한 휴지통 문서 참조 보존 |
| 기존 사진 참조 | document.media와 본문 mediaId를 기존 검증기로 추출 | 기존 문서, 게시 주소, 스냅샷, 업로드 예약 중 하나라도 쓰면 보존 |
| 공유 `shares` | 추측 불가 public token, 대상 file/snapshot, 만료 nullable, revokedAt, revision | 공개 판단은 요청마다 서버 시각으로 수행 |
| 스냅샷 `snapshots` | document_id, source_revision, 고정 렌더링 결과, 현재 version | 초안 삭제와 독립. 명시적 갱신에서만 version 전환 |
| 스냅샷 자산 참조 | snapshot version + 불변 게시용 object | 사진은 재인코딩본만. 가변 `/media/<id>` 주소 재사용 금지 |
| 정리 작업 `cleanup_jobs` | object_id/generation unique, 시도 횟수, 상태, 재시도 시각 | 삭제 성공을 확인하기 전 장부를 제거하지 않음 |

동일 이름 업로드는 서로 다른 파일 ID다. 이름 변경은 바이트·공유 주소를 바꾸지 않는다. 첫 버전은 파일 교체와 해시 기반 전역 중복 제거를 하지 않는다. 문서의 파일 링크는 일반 URL 문자열만으로 표현하지 않고 검증 가능한 내부 fileRef 노드와 파일 메타데이터로 표현한다. 렌더러·편집기·백업이 함께 이해해야 한다.

| 동작 | 글·보관함 | 공개 주소 | 바이트 |
| --- | --- | --- | --- |
| 글 휴지통/기한 경과 | 기존 30일 규칙 | 게시 사진·파일 주소·공유 스냅샷 전부 유지. 글 삭제 화면의 철회 체크박스 제거 | 다른 글·보관함·공유·스냅샷 참조를 보존 |
| 글에서 파일 제거 | 해당 문서 참조만 제거 | 공유 유지 | 독립 보관 참조 때문에 유지 |
| 파일 휴지통 | 새 삽입 대상에서 제외, 30일 복원 | 기존 공개 링크 유지. 철회는 보관함에서 별도 조작 | 다른 문서가 참조하면 계속 보존 |
| 작성 공간 파일 영구 삭제/기한 경과 | 독립 보관 참조 제거 | 공개 링크 유지. 보관함의 배포물 철회/삭제가 별도 명시 조작 | 다른 참조가 있으면 물리 삭제하지 않고 이유·용량 표시 |
| 공유 철회/만료 | 소유자 파일은 유지 | 즉시 이후 요청부터 404 | 파일 원본 유지. 스냅샷 현재본은 갱신/재발급을 위해 비공개 유지 |

휴지통에서 복원 가능한 문서 참조와 실행 취소 중인 파일은 정리 후보가 아니다. 기존 알 수 없는/깨진 문서가 있으면 그 문서가 쓸 수 있는 기존 원본의 정리를 보수적으로 보류한다. 장부가 완성되지 않은 데이터를 고아로 판정하지 않는다.

## 공유 API와 격리

소유자 경로는 기존 owner 검사와 쓰기 Origin 검사를 유지한다. 파일 목록/업로드/이름 변경/휴지통, 공유 생성/연장/철회/재발급, 스냅샷 생성/갱신, 정리 실행을 별도 작은 핸들러로 분리한다. worker.ts의 라우팅 아래 연결한다. 공개 경로는 GET/HEAD만 허용한다.

공유 기본은 만료 없음. expiresAt은 UTC로 저장하고 `now >= expiresAt`부터 404. 연장은 같은 주소의 기한만 변경한다. 철회는 revokedAt 기록, 재발급은 옛 주소 비활성화와 새 token 생성을 한 DB 트랜잭션에서 수행한다. 오래된 요청이 재발급을 되돌리지 못하도록 revision을 검사한다. 철회한 주소를 연장만으로 되살리지 않는다. 재발급 재시도는 작업 ID로 중복 발급을 막는다.

GET/HEAD의 성공·오류 모두 no-store. Range나 조건부 요청이 권한 검사보다 먼저 처리되지 않게 한다. 첫 버전은 Range를 무시하고 검사 후 전체 200 응답하는 방법을 검증한다. 이미 내려받은 사본과 철회 전에 시작된 전송 회수는 보장하지 않는다. URL에 원본 key·개인 식별자·인증 정보를 넣지 않는다.

PNG/JPEG만 형식 검증 뒤 inline 가능. 나머지는 업로드 Content-Type을 믿지 않고 application/octet-stream, attachment, nosniff, `Content-Security-Policy: sandbox; default-src 'none'`로 제공한다. filename의 개행·제어문자·경로 및 인코딩 오류를 방어한다. HTML/SVG는 미리보기에도 실행하지 않는다. 공개 스냅샷 HTML은 업로드 HTML과 다른 경로이며 공통 렌더러 출력만 사용한다. 스크립트·폼·프레임 금지 CSP와 noindex 헤더/메타를 기본 적용한다. 기존 영상 블록은 실행 iframe 대신 검증된 외부 링크로 표시하는 안을 제안한다.

파일당 상한은 정확히 20 * 1024 * 1024 bytes. 헤더와 실제 읽은 바이트 둘 다 검사한다. 여러 파일은 파일별 순차 업로드/성공·실패/재시도 표시로 메모리를 제한한다. Content-Length 누락·거짓 값, 중단, 20MiB+1을 시험한다. 150GB 및 플랫폼 최대 파일 크기를 제품의 보장으로 쓰지 않는다.

## 스냅샷 원자적 갱신

문서 revision을 고정하고 저장된 사본에서 공통 렌더러와 재인코딩 사진을 준비한다. 별도 불변 자산 key를 사용하고 임시 작업으로 묶는다. 준비 완료 후 document revision과 share revision을 확인하여 현재 snapshot version 포인터를 한 번에 교체한다. 중간 실패면 이전 페이지가 그대로 남는다.

초안 편집이나 기존 사진 재게시가 스냅샷 내용을 바꾸면 실패다. 스냅샷 사진 주소도 해당 공유의 만료·철회·version을 매번 검사한다. 지원이 승인한 조건에 따라 이전 version 자산은 갱신 성공 시각부터 최대 5분 공개 응답을 유예한다. 기존 페이지 열람자만이 아니라 옛 URL을 아는 누구나 이 시간에 접근할 수 있다. 그 사이 여러 번 갱신돼도 각 version의 교체 시각으로 계산한다. 공유 철회·만료·재발급의 옛 token은 유예보다 우선하여 다음 요청부터 404다. 5분 정각부터 옛 자산 응답을 중단하되 원본 강제 삭제 기한은 아니다. 다른 글·공유 참조가 있으면 바이트를 보존한다. 장시간 멈췄던 옛 페이지의 사진은 다시 열어야 할 수 있다. 현재 version 자산은 계속 제공한다. 이전 HTML 응답 직후 갱신, 유예 직전/정각, 유예 중 철회·재발급을 시험한다. 파일 링크는 별도 파일 공유의 만료·철회를 따르며, 스냅샷 자체 만료가 이미 독립 공유된 파일 주소까지 철회하지 않는다는 점을 안내한다.

## 정리의 실패·재시도·동시 실행

D1과 R2를 한 트랜잭션으로 취급하지 않는다. 모든 새 바이트를 업로드 예약으로 등록한 뒤 put하고, 참조를 붙일 때 objects.ready 상태를 조건으로 확인한다. 저장·게시·스냅샷 전환과 참조 갱신은 같은 DB 트랜잭션이어야 한다.

정리는 원보드를 연 소유자 요청으로 제한된 개수씩 실행한다. DB에서 참조 없음·예약 없음·세대 일치를 조건으로 ready→deleting과 정리 작업 생성을 원자적으로 수행한다. 이 상태에서 새 참조 추가는 실패시켜 다시 준비하도록 한다. 단순히 참조 수를 읽고 R2를 지우는 순서는 금지한다. 그 사이 다른 문서가 연결될 수 있다.

객체 삭제 후 장부를 완료 처리한다. 삭제 뒤 응답 유실은 다음 실행에서 같은 key 삭제/없음 확인으로 성공 처리한다. 실패는 장부와 재시도 시각을 남기고 다음 소유자 방문 또는 수동 재시도로 이어간다. 예약 실행이나 상시 백그라운드 서비스는 약속하지 않는다. 작업 임대가 끝난 업로드는 ready로 승격되지 못하도록 fencing 조건을 둔다. 업로드 후 DB 실패한 객체도 작업대장을 통해 회수한다.

화면은 논리 삭제·정리 대기·실제 확보한 용량을 구분한다. 계정 총량을 모르면 비율/잔여량을 추정하지 않고 원보드가 추적하는 바이트만 보여 준다. 코드 변경 전부터 R2에 남아 있던 미등록 객체는 로컬 fixture로 inventory 경로를 설계하되 운영 정리는 별도 승인 전 실행하지 않는다.

## 기존 데이터·세 저장소·백업
